# Formbricks eval

Runs a mission on the [Formbricks lab app](../lab-formbricks/README.md) through a coding agent and measures it: pass or fail from the database, wall time, tokens and cost from Claude Code's own output. The same mission runs through different browser interfaces, called arms, so the interface is the only variable.

This package is separate from the lab app on purpose. The agent's working root is the Formbricks source, `apps/lab-formbricks/formbricks`, and nothing else; missions, results and transcripts live here, and the lab app's Page Objects in the folder around that source, where the agent cannot read them (see [what the agent can read](#what-the-agent-can-read)).

It runs by hand, on a Mac or [on a hosted runner](#on-a-hosted-runner). It is never part of CI or `pnpm check`; only its unit tests are.

The package also holds [the startup lane](#the-startup-lane), which checks that the shipped `ayme` skill routes an agent to the right references. It needs none of what follows but Claude Code and the token.

## Prerequisites

- The lab app prepared and running: `pnpm lab:prepare` and `pnpm lab:dev` in `apps/lab-formbricks`. `lab:prepare` also builds the Ayme packages the arms with Ayme serve to the page (see [how Ayme reaches the page](#how-ayme-reaches-the-page))
- Docker Desktop, running
- Google Chrome
- A long-lived Claude Code token in this package's git-ignored `.env.local`, created with `claude setup-token`:

  ```sh
  CLAUDE_CODE_OAUTH_TOKEN=<the token>
  ```

  A `CLAUDE_CODE_OAUTH_TOKEN` already exported in the shell wins over the file. The token reaches only the agent's environment; it is never written to a run's files. Claude Code itself keeps it out of the MCP servers and Bash commands it starts: with Claude Code 2.1.281, neither a stdio MCP server nor a Bash command sees `CLAUDE_CODE_OAUTH_TOKEN`.

The run checks these first and names whichever is missing before anything starts. One of them is a clean lab app folder: `apps/lab-formbricks`, submodule included, with no untracked or modified file (gitignored files do not count), because the agent would see one in the submodule, and the run's server serves the Page Objects beside it.

## One run

From this directory inside `devbox shell`:

```sh
pnpm eval:run -- --arm playwright-mcp
pnpm eval:run -- --arm playwright-mcp-with-ayme-page-objects
pnpm eval:run -- --arm playwright-mcp-with-ayme-webmcp
pnpm eval:run -- --arm playwright-cli
pnpm eval:run -- --arm playwright-cli-with-ayme-page-objects
pnpm eval:run -- --arm playwright-cli-with-ayme-webmcp
pnpm eval:run -- --arm agent-browser
pnpm eval:run -- --arm agent-browser-with-ayme-webmcp
pnpm eval:run -- --arm ayme-goal-loop-off
pnpm eval:run -- --arm ayme-no-page-objects-goal-loop-off
```

Options: `--model` (default `haiku`, Claude Code's alias for the current Haiku), `--timeout-seconds` (default `600`, the task turn's; see [what is measured](#what-is-measured)), `--mission` (default `rename-survey-and-question`; see [missions and arms](#missions-and-arms)). Every run calls the model and costs money.

The run:

1. Checks the preconditions, names the missing ones and stops; builds Formbricks's database package on the first run.
2. Seeds its own user, organization and workspace, and the mission's survey when it has one, through Formbricks's database package. Nothing earlier is cleared. It then waits until Formbricks's background worker has projected the new rows into its authorization store; without that, sign-in lands on "create organization".
3. Opens the mission's start page in a fresh browser profile, with the browser the arm uses: signed in on the seeded survey's editor, or, for a mission that starts signed out, the sign-in page in a profile that holds no session. Either way the route is compiled before the agent's browser opens it.
4. Runs the arm's setup, if it has one: whatever its interface needs outside the measured window (see the arm table). The measured agent installs and downloads nothing.
5. Starts Claude Code on the Formbricks submodule in the lab app folder, with the arm's interface and nothing else, from a fresh, empty configuration folder inside the run folder, which is deleted afterwards. It sends the setup message, waits for the agent's answer, then sends the shared prompt with the arm's interface line. The measured window is that second message alone.
6. Reads the seeded workspace's surveys back from the database and decides pass or fail from the mission's expected end state. The agent's final message is kept but has no say.
7. Moves any file the agent created in the lab app folder into `agent-files/` (nothing is deleted; modified tracked files stay and are recorded), closes what the arm's setup started, whether the run passed, failed, timed out or could not complete (see [how a run ends](#how-a-run-ends)), and writes everything under `results/runs/<run id>/`.

The exit code is `0` for a pass, `1` for a fail and `2` when the run could not complete.

### How a run ends

Everything a run starts is closed before the run returns, in the order the setups started it, last first: the agent's own CLI sessions (`playwright-cli close`, `agent-browser close --all`), the browser, the run's `ayme mcp` with the socket and proxy in front of it, and the init script it wrote.

`ayme mcp` runs in a process group of its own, and stopping it signals the group: SIGTERM, then SIGKILL to whatever is left after five seconds. Stopping the server alone is not enough. It builds the Page Objects with an esbuild service, a child process that inherits the server's standard error, which is a pipe to the harness. Killed while a request of that service was unanswered, such as its once-a-second ping, the server left the service behind for good, holding that pipe open, and Node does not exit while a pipe is open: a suite that had written its summary never ended, and its hosted job ran until it was cancelled. Measured on one machine, stopping an idle server that way left the service behind about once in twenty-five. So the stop also waits until the server's standard streams have ended, not only until it has exited. If a process that left the group still holds them two seconds after the group was killed, the harness lets go of its own end and logs that. While the server runs, the group is also killed when the harness itself exits or is interrupted, since Ctrl+C no longer reaches it.

`pnpm eval:run` and `pnpm eval:suite` have a backstop behind that, so no leak can hold a hosted job again. Once the command's work is done, Node ends by itself with the command's exit code. If the process is still alive five seconds later, something a run started was not closed: the command logs what Node still holds open, by kind and count as `process.getActiveResourcesInfo()` names it and without its own output streams (`1 PipeWrap` is one pipe to a process that outlived its run), and exits with the code it was going to exit with. A command that ends by itself logs nothing, so the line only ever means a leak to fix.

## What is measured

The agent gets two messages in one Claude Code session, over its stream-json input, and answers each as its own turn:

1. The setup message (`setup-prompt.txt`): get ready to work in the open page; load the arm's skill, named, with the Skill tool, or, for an arm without one, don't look for a skill; read no files, don't use the browser, and reply ready. The Ayme arms alone are told instead to read the references their skill points to, and no file outside that skill's folder. It names no app and no task, and differs between arms only in that skill and that reading. Claude Code's start-up, the MCP server's tool list and the skill load land in this turn, with the references for the Ayme arms. An unnamed "load your skill if you have one" left the agent skipping the load in some runs and loading the skill in the measured turn instead.
2. The task message (`prompt.txt`): the shared mission text with the arm's interface line, unchanged from a single-message run.

Every measured figure is the task turn's. Wall time runs from sending the task message to its `result` event. Tokens are that turn's usage. Cost is the session's cumulative cost at the end of the task turn minus its value at the end of the setup turn, since Claude Code's `total_cost_usd` accumulates over the session. Tool calls are those made after the task message. The setup turn's own time, tokens, cost and tool calls are kept in the result's `setupTurn` and are never added to the measured figures.

The setup turn has its own 120 second timeout. A setup turn that runs out of it, or ends with an error, is a run that could not complete: nothing is measured and the transcript stays in the run folder. The run's `--timeout-seconds` covers the task turn.

With a task as small as the default mission's, the agent's start-up and skill load would otherwise be a large share of every number, and a share that differs between arms. The longer mission (see [missions and arms](#missions-and-arms)) is where the setup matters less.

## A suite

From this directory inside `devbox shell`:

```sh
pnpm eval:suite -- --runs 3
```

Options: `--arms` (comma-separated, default every arm in [`src/arms.ts`](src/arms.ts)), `--runs` per arm (default `3`), `--model` (default `haiku`), `--timeout-seconds` (default `600`), `--mission`. Every run uses the same timeout and settings and seeds its own mission. Every run calls the model and costs money; the smallest suite is one arm and one run:

```sh
pnpm eval:suite -- --arms playwright-mcp --runs 1
```

The suite:

1. Checks the preconditions before it creates anything. Each run checks them again, so a lab app that goes down mid-suite is caught.
2. Warms the lab app, outside every measured window: Turbopack compiles each route and each server action on its first use, which takes 15 to 25 seconds a screen on a fresh dev server and, left to the first run, would land inside that run's measured window (see [the lab README](../lab-formbricks/README.md#timeouts)). So it seeds a throwaway user without a survey and walks every screen the missions pass through, by the steps they take: the sign-in page, signed out; then, signed in, the root the sign-in form sends the browser to and the screen where a new organization creates its first survey, from which it starts a survey from scratch to reach the editor; there it saves and closes, which publishes the survey and opens the summary page with its share dialog, closes the dialog, opens the editor again from the summary and saves and closes once more; then the survey list. The survey it saves is its own, so no run's data changes. It never starts or restarts the lab app.
3. Runs the arms round-robin (run 1 of each arm, then run 2, and so on), so a suite that stops early still holds comparable runs.
4. Writes its manifest and summary to `results/suites/<suite id>/`.

The first run that cannot complete (a missing precondition, an unreachable lab app, a failed seed) ends the suite. The runs stored so far are summarized and the summary says the suite stopped early. A failed verdict is a result, not an error.

## On a hosted runner

The [Formbricks eval workflow](../../.github/workflows/eval-formbricks.yml) runs a suite on a standard GitHub-hosted Ubuntu runner, started by hand only (Actions, Formbricks eval, Run workflow). It never runs on pull requests or pushes. Its inputs are the mission, the arms (empty for every arm), the runs per arm, the model (`haiku` unless given), and `qualify_only`, which prepares the lab app and runs `lab:qualify` without starting an agent, so it calls no model and costs nothing.

The job installs the pinned Claude Code, runs `lab:prepare`, starts `lab:dev` in the background and waits for the sign-in page, then runs `pnpm eval:suite`. It reads one repository secret, `CLAUDE_CODE_OAUTH_TOKEN`, the agent's Claude Code login; a qualify-only run does not get it. Only people with write access to the repository can start it, and runs from forks never get the secret. The job summary holds the machine (OS, runner image, CPUs, memory) and the suite summary; the `eval-formbricks-results` artifact holds `results/` with the same machine record, and `lab-formbricks-log` holds the lab app's output. The repository is public, so its Actions logs and artifacts are too.

A runner is not a Mac, so its timings are not comparable with a Mac's: compare runs from the same kind of machine only. One eval runs at a time, since every paid run uses the same Claude Code login. A runner's summary is committed in a folder of its own, with the machine beside it, so it never replaces a Mac's summary of the same day: the first is [`summaries/2026-10-06-hosted-runner/`](summaries/2026-10-06-hosted-runner/summary.md), and the latest, with ten runs per arm, are [`summaries/2026-10-24-hosted-runner/`](summaries/2026-10-24-hosted-runner/summary.md) and [`summaries/2026-10-24-hosted-runner-sign-in-create-and-revise-survey/`](summaries/2026-10-24-hosted-runner-sign-in-create-and-revise-survey/summary.md).

## The summary

```sh
pnpm eval:report                         # the newest suite
pnpm eval:report -- --suite <suite id>
pnpm eval:report -- --publish            # also write summaries/<date>/
```

The report command rebuilds `summary.md` and `summary.json` from the stored runs listed in the suite's manifest. It launches no agent and needs neither the lab app nor a Claude Code token, so a change to the report costs nothing to re-run. The suite writes the same summary when it ends.

Per arm the summary shows:

- passes out of the runs stored for the arm; failed and timed-out runs count in the runs;
- the median, lowest and highest of wall time, tokens and cost, all of the task turn alone. Tokens are the agent's input, cache creation, cache read and output tokens added up. For a run stored while the Goal Loop arms existed, the cost is its combined cost, the agent's plus the Goal Loop's. A failed run still contributes its time, tokens and cost. A run without a figure counts in the passes and the runs but not in that column; the cell then says how many runs it rests on, or `unknown` when none has it. With an even count the median is the mean of the two middle values.

It also records what a rerun must match: the Claude Code version, the model, the pinned browser interface of each arm (the Playwright CLI, Playwright MCP, `agent-browser` and `@ayme-dev/mcp` versions), the browser, the Ayme and Formbricks commits, the timeout and the date. If the runs of a suite differ in one of these, the summary lists every value and says so.

`--publish` writes the summary, formatted with the repository's Prettier, to `summaries/<date>/summary.md` and `summary.json`, dated by the day the suite started; a suite of a mission other than the default one goes to `summaries/<date>-<mission>/`. That folder is meant to be committed; a second summary for the same day replaces the first. `results/` stays ignored, so transcripts, prompts and run folders are never committed.

A suite adds `results/suites/<suite id>/` with its manifest (`suite.json`) and summary.

The browser profile is deleted after the run; the seeded data stays.

## Missions and arms

A mission is data in [`src/missions.ts`](src/missions.ts): the values to seed, the screen the agent starts on, the task's steps and the end state to expect. The values the agent has to type carry a short random nonce, so typing length does not dominate the measurement; the full run id stays in the seeded user, organization and workspace names, where uniqueness matters. The task message is the same shape for every mission: the shared text, the arm's interface line, where the browser is, the mission's numbered steps, and what must hold before the agent finishes. The verdict is a pure function of the mission and the seeded workspace's surveys, read from the database after the run.

| Mission                            | Start                                                                | Task                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Pass when                                                                                                                                                                                      |
| ---------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rename-survey-and-question`       | Signed in, on the editor of a seeded survey with one question        | Rename the survey, change its question's headline, save and close, confirm the summary page shows the new name. Two page object calls' worth of work; the published table rests on it.                                                                                                                                                                                                                                                                         | The seeded survey has the expected name and its question the expected headline.                                                                                                                |
| `sign-in-create-and-revise-survey` | Signed out, on the sign-in page; a user and workspace with no survey | Sign in with the seeded email and password, which this mission's task message carries; create a survey from scratch; name it and set its question's headline; save and close; close the share dialog on the summary page; open the survey in the editor again; change the headline to a second text; save and close; confirm the summary page shows the survey's name. Eight page object calls, across four screens, so an interface's fixed costs weigh less. | The workspace holds exactly one survey, with the expected name, and its first question's headline is the second text. Two surveys, the first headline left in place, or no survey at all fail. |

The default mission stays `rename-survey-and-question`, so its runs stay comparable with the published numbers; the other is chosen with `--mission`. For a mission that starts signed out, no arm is signed in by the harness: the Playwright MCP arm's init page and the Playwright CLI arm's session open the sign-in page in a profile with no session, and the headless Chrome of the arms with Ayme opens it and pairs it with the run's server. Sign-in in Formbricks ends in one full page load; the new document runs the server's init script again, and the Agent Connection follows the tab through it, as through the client-side navigations after it (see [how Ayme reaches the page](#how-ayme-reaches-the-page)).

An arm is an entry in [`src/arms.ts`](src/arms.ts): its one prompt line, its MCP servers, the built-in tools it leaves the agent, the permission rules that let it use its interface (and any that stay denied), its own preconditions, and an optional setup that runs before the measured window. Everything else is shared, in [`src/claude.ts`](src/claude.ts) and [`src/prompt.ts`](src/prompt.ts): one model, Haiku unless `--model` says otherwise, at the same `medium` thinking effort (`--effort`), which keeps the model from pausing for minutes before a single step of a short task, the setup message, a 600 second timeout for the task turn, and an isolated Claude Code configuration: a fresh configuration folder per run, an environment stripped of every `CLAUDE*`, `ANTHROPIC*` and `AYME_*` variable of whoever launches the eval, no project settings, no user settings or skills beyond that empty folder, and no MCP servers beyond the arm's own. The agent keeps read-only file tools, so it can look at the Formbricks source but can change the app only through its browser interface; [what the agent can read](#what-the-agent-can-read) says where that ends. The result records the tools, MCP servers, skills and plugins the agent was given and the folder it ran in; the skills and plugins listed are the ones built into Claude Code, which an isolated configuration still has.

### What the agent can read

Every arm's agent runs in the Formbricks submodule, `apps/lab-formbricks/formbricks`, the source the task message says its working directory holds. Claude Code reads files in its working folder and in the folders a run adds with `--add-dir`: an arm's skill in the run's configuration folder and, for the CLI arms, the output folder. That holds for its file tools, `Read`, `Glob` and `Grep`, and for the read-only shell commands it runs without a permission rule in the arms with Bash, such as `cat`, `ls` and `rg`. Under the runs' permission mode, `dontAsk`, anything outside those folders is denied instead of asked for.

The lab app's folder is the submodule's parent, so everything of Ayme in it is out of every arm's reach, the baselines' included: the Page Objects in `.ayme/pom/` and the entries beside them, their qualification in `tests/`, the lab README that describes them, and `.ayme/init-script.js`, which the run's server writes there. The server builds the Page Objects in memory and writes nothing else. `ayme mcp` itself still starts in the lab app's folder, where it finds the entry it serves.

A result stored while the working folder was the lab app's folder itself, where an agent could open all of that, has no `isolation.workingDirectory`; the transcript's `system/init` event names the folder.

What a page loads is another matter: in the arms with Ayme the browser itself fetches the built Page Objects from the run's server, minified, so an agent's browser tool can reach what its page runs. The baselines' pages load nothing of Ayme and no server runs for them.

Formbricks's own `CLAUDE.md`, `AGENTS.md` and `.claude/` are in the working folder. The shared configuration loads user settings alone (`--setting-sources user`), so Claude Code loads none of them: the agent's context and its skill list are what they were.

This was checked with Claude Code 2.1.322 and the runs' own arguments, against a local stand-in for the model that asked for each read in turn. From the submodule every read of the lab app's folder was denied, through `Read`, `Glob` and `Grep` and through `cat`, `ls`, `rg`, `grep`, `find` and `cd` in Bash, while reads inside the submodule went through; the same reads succeeded with the lab app's folder as the working folder. The pinned 2.1.281 is expected to do the same; a read an agent was denied counts in its result's `agent.permissionDenials`.

### How Ayme reaches the page

The lab app is unmodified Formbricks and ships no Ayme (see [the lab README](../lab-formbricks/README.md#ayme-in-the-lab-app)). `playwright-mcp`, `playwright-cli` and `agent-browser` drive it as it is: they load no init script and start no `ayme mcp`. Every other arm gets Ayme and the lab app's Page Objects from outside, from an `ayme mcp` that serves them, set up before the measured window:

1. **The server, before the browser.** The harness starts `ayme mcp` from the workspace's `@ayme-dev/mcp` in the lab app's folder, with `--port` on the first port of the range a page scans, 9350 to 9365. There the server finds [`.ayme/page-objects.ts`](../lab-formbricks/.ayme/page-objects.ts), builds it with this checkout's `@ayme-dev/ayme`, serves the build on its own port and writes `.ayme/init-script.js`, which names that port and which git ignores. The setup removes an earlier init script first, waits until the server says it wrote its own, and checks that the script names the run's port and turns WebMCP publication on exactly when the arm wants it. The run refuses to start while anything listens in that range, such as another coding agent's `ayme mcp`, because a page pairs by itself only with exactly one server, and while the packages the server needs are not built, which `lab:prepare` does. After the run the server is stopped, with the esbuild service it started (see [how a run ends](#how-a-run-ends)), and its init script removed. Its standard error is kept in the run folder.
2. **What the server is started with.** This is all that differs between the kinds of arm on the server's side:

   | Arms                                                                                                   | `ayme mcp` gets                           | The page then                                                                                                                                  | The agent gets the server                                                                                            |
   | ------------------------------------------------------------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
   | `ayme-goal-loop-off`, `playwright-mcp-with-ayme-page-objects`, `playwright-cli-with-ayme-page-objects` | nothing more                              | offers `snapshot`, the Browser Tools and the screen's Page Object Tools to the server, and publishes nothing through WebMCP                    | yes, as `ayme`; in the two `*-with-ayme-page-objects` arms through the proxy that offers the Page Object Tools alone |
   | `ayme-no-page-objects-goal-loop-off`                                                                   | `--page-objects .ayme/no-page-objects.ts` | offers `snapshot` and the Browser Tools and no Page Object Tool                                                                                | yes, as `ayme`                                                                                                       |
   | `playwright-mcp-with-ayme-webmcp`, `playwright-cli-with-ayme-webmcp`, `agent-browser-with-ayme-webmcp` | `--webmcp`                                | also publishes the screen's Page Object Tools and the read tool `page_objects` through `document.modelContext`, and nothing else of Ayme there | no                                                                                                                   |

   In the arms through WebMCP the server only serves the files. The page still pairs with it, since the init script turns the Agent Connection on, but no agent is given the server and nothing calls it.

3. **The browser.** A headless system Chrome on the profile the harness prepared, launched by the harness with `bypassCSP`, the `local-network-access` permission and the server's init script on its context (`addInitScript`), opens the mission's start page and stays open for the run. Formbricks's content security policy allows neither the served modules nor the server's loopback WebSocket, and Chrome asks before a page reaches `127.0.0.1`. Every browser the harness launches also gets Chrome's WebMCP flag, `--enable-features=WebMCP`, which supplies `document.modelContext`.
4. **The pairing.** In the page, the init script loads Ayme's runtime and the Page Objects from the server and turns the Agent Connection on. On `localhost` the tab looks for a server as it loads and pairs with the run's by itself. The setup waits until the tab holds the pairing the server welcomed it with and until the server has logged it, in every arm with Ayme. The scan's probes of the fifteen ports without a server are refused, which Chrome logs as console errors on the document that scans.
5. **The start screen's tools, read where the agent will read them.** The start screens' tools are `SignInPage.logIn` on the sign-in page and `SurveyEditorPage.fillSurveyForm` on the editor. In the arms whose agent gets the server, the setup reads the server's tool list, with a `tools/list` on the server's stdio before the agent connects to it, and waits until it lists the start screen's tool; the page publishes nothing through `document.modelContext` there. The setup sends no `initialize`, so the agent's stays the session's one, and what the server notes as shown to its agent is what the agent's own first list notes. In the arms through WebMCP the setup reads `document.modelContext.getTools()` in the page and waits for the same tool; `page_objects` is listed beside it. What it read is recorded in the result's `setup`.
6. **Documents the agent's own tool loads.** In the arms where Playwright MCP, the Playwright CLI or agent-browser attaches over CDP to the harness's Chrome, none of the three is given the init script. The harness's own Playwright added it to the browser's context and stays attached for the whole run, so Chrome runs it, with the content security policy bypassed, in every document of that context, whichever client navigated the page: a page the agent's tool loads again, and the document after the full page load that ends sign-in, pair again and offer the next screen's tools.

### The Ayme arms

The agent gets Ayme's MCP server, named `ayme`, as its one MCP server, and the read-only file tools. Nothing else: no Playwright interface, no Bash. The server is the run's `ayme mcp` from the workspace's `@ayme-dev/mcp`, which also serves the page its runtime and its Page Objects (see [how Ayme reaches the page](#how-ayme-reaches-the-page)), so the server and the page's Ayme are this checkout's. Its own tools stay allowed: `ayme_connect` only returns a link, which the agent has no tool to open, and a server busy with its tab ignores any other tab's scan, so the agent cannot move the server away from the harness's tab; `ayme_list_tools` and `ayme_call` are the fallbacks the server offers every agent. Both Ayme arms run against the same lab app; they differ in the entry the server serves, the lab app's one switch (see [the lab README](../lab-formbricks/README.md#lab-switches)). The Goal Loop arms, `ayme-goal-loop-on` and `ayme-no-page-objects-goal-loop-on`, were removed; the remaining arms keep the `goal-loop-off` suffix so their stored results stay comparable by arm name.

Set up outside the measured window:

- **The server, paired before the agent starts.** A coding agent normally starts `ayme mcp` itself, and a tab of the app on `localhost` pairs with it by itself when it loads or gains focus. Claude Code starts its MCP servers only when the agent starts and reads their tool lists at once, so a tab that paired then would reach the agent through a tool-list change somewhere around its first turn, before it in some runs and after it in others. So the harness starts the server itself, before the agent and before the browser, in the run's process, and hands its stdio to Claude Code through a small proxy over a Unix socket: the `ayme` server Claude Code starts is that proxy, written into the run folder, and the agent's first tool list already holds the page's tools. What the server says before the agent connects, the tool-list change of a pairing no agent saw, is dropped, but for the answers to the setup's own `tools/list`.
- **The page.** The browser and the pairing are as [above](#how-ayme-reaches-the-page). The setup then waits until the server lists the start screen's Page Object Tool; a page that offers `goal` fails the setup. Without page objects it waits for `snapshot` instead, checks two seconds later that the server lists no Page Object Tool, and that the page is still at the start page's address; what it saw, with the time the pairing took, is recorded in the result's `setup`. The pairing then follows the tab wherever the task takes it: the tab keeps it across a full page load, such as the one that ends sign-in, and across the client-side navigations between the survey screens, and the server tells the agent each time the screen's tools change. A call the page navigates away from before answering gets an error saying so, with the outcome unknown. The browser is closed and the server stopped after the run.
- **The skill.** The repository's [`skills/ayme`](../../skills/ayme/SKILL.md), the skill consumers install, so the eval measures what ships. It is the same for every Ayme arm, copied with its references into the run's fresh Claude Code configuration folder under `skills/`, as the Playwright CLI arm's skill is; the permission rules allow only this one. The agent is given read access to that copy, and to nothing else outside its working folder. No Read permission rule is added: `--add-dir` is expected to let Read reach the copy, as the Playwright CLI arm's stored runs read their added output folder under the same permission mode, and the first rerun confirms it; a denied Read would show in the setup turn. The setup turn loads the skill and reads the references it points to, so the measured turn starts with them in context. The skill names no app and no task.

### The Playwright MCP arm with Ayme's Page Object Tools

`playwright-mcp-with-ayme-page-objects` compares a browser tool with and without Ayme, where the other arms compare Ayme with a browser tool. The agent gets two MCP servers: `playwright`, the pinned Playwright MCP exactly as the Playwright MCP arm configures it but for how it reaches the browser, and `ayme`, the run's `ayme mcp` through a proxy that offers the page's Page Object Tools alone. The built-in tools, permission rules, setup message and task message are the Playwright MCP arm's; the interface line adds its one sentence, and `mcp__ayme` is allowed beside `mcp__playwright`. No skill is loaded: the Playwright MCP arm has none, and the two arms differ in nothing else the agent reads. The server serves the lab app's Page Objects, as for `ayme-goal-loop-off`.

Set up outside the measured window, as [the Ayme arms](#the-ayme-arms) are, with two differences:

- **One browser for both servers.** The setup launches the headless Chrome on the run's profile as for the Ayme arms, init script included, with a remote-debugging port on a free loopback port, and waits for the pairing and the start screen's Page Object Tool in the same way. Playwright MCP is then started with `--cdp-endpoint` on that port instead of a browser of its own: it attaches to the running browser, takes its first context, the profile's, and adopts the open tab as its current one, so the agent's first snapshot is the page that paired. The browser, profile and headless switches describe a launch that never happens with a CDP endpoint, so they are left out; `--no-webmcp` stays, and the page publishes nothing through WebMCP in this arm anyway, so the page's own tools reach the agent through `ayme` alone. Playwright MCP is not given the server's init script: the harness's Playwright added it and stays attached, so it runs in every document Playwright MCP loads (see [how Ayme reaches the page](#how-ayme-reaches-the-page)). The init-page script, which Playwright MCP runs on an adopted tab too, acts only on a blank page, so it opens the start page in any tab the agent adds, as in the Playwright MCP arm. The pairing happens before the agent starts; the attachment, when Claude Code starts the server, lands in the setup turn, outside the measured window. The port is chosen by the setup, so the `playwright` entry of `mcp.json` is the setup's, written beside the arm's `ayme` entry once the setup has run.
- **A proxy that hides everything but the Page Object Tools.** Ayme's server lists its own tools, the Browser Tools, `snapshot` and the Page Object Tools, and nothing in it hides any; the harness's proxy does, in a filtering mode this arm alone uses. It reads the newline-delimited JSON-RPC messages, whole whatever the chunks: a `tools/list` answer keeps the Page Object Tools and drops the rest, a `tools/call` of any other tool is answered with a JSON-RPC error without reaching the server, and every other message, `notifications/tools/list_changed` included, passes through unchanged. A Page Object Tool is known by its name, `<class>.<action>`: the server's tool list carries no annotation of what published a tool, every other tool of the page and the server carries no dot, and a Peek Tool, the one other dotted family, starts with `peek.`. The result's `setup.proxy` records that the proxy filtered and the start screen's tools it left; the task turn's transcript shows what the agent was offered after each screen change. The server's standard error and the proxy are kept in the run folder as for the Ayme arms.

The result records `@playwright/mcp` as the arm's browser interface; the `@ayme-dev/mcp` version is in `setup.server`.

### The Playwright CLI arm with Ayme's Page Object Tools

`playwright-cli-with-ayme-page-objects` is the CLI's twin of the arm above: the Playwright CLI exactly as [its arm](#the-playwright-cli-arm) configures it, skill, tools, allowed and denied commands, plus the `ayme` server through the same filtering proxy, with `mcp__ayme` allowed beside the CLI. The interface line is the Playwright CLI arm's plus the same sentence; the setup message is the CLI arm's. The result records `@playwright/cli` as the browser interface and `setup` holds what the Ayme setup established, the proxy's filtering and the remote-debugging port included.

The browser is shared as for the MCP twin: the setup pairs the page first, on a Chrome with a remote-debugging port, then starts the CLI session with `playwright-cli attach --cdp=<endpoint>` instead of `open`. The CLI's daemon reads the same `PLAYWRIGHT_MCP_*` variables as Playwright MCP, so the session's environment carries `PLAYWRIGHT_MCP_CDP_ENDPOINT` in place of the browser and profile variables, which describe a launch that never happens; a session the agent restarts attaches to the same browser again. `open` is not used because it always navigates once the session is up (`goto` the URL given, or `about:blank` without one), a second load of the paired page; `attach` takes a snapshot instead and leaves the tab as it is. The daemon adopts the browser's first context and its open tab, and the snapshot names the page, which the setup checks is the start page, as the CLI arm checks what `open` reports. The session is closed before the Ayme setup closes the browser.

### The arms with Ayme's Page Object Tools through WebMCP

`playwright-mcp-with-ayme-webmcp` and `playwright-cli-with-ayme-webmcp` give the agent the page's tools the way Playwright itself surfaces WebMCP, instead of through Ayme's MCP server and the harness's proxy. Each is its browser tool's arm with three differences and nothing else the agent reads: the page gets the lab app's Page Objects served with `--webmcp`, the browser tool's WebMCP switch is on, and the interface line adds one sentence: the page's own tools, which Playwright lists as WebMCP tools, include the Page Object Tools of the screen the browser is on; prefer one of them whenever it does the step. The Playwright CLI's own skill already says to prefer a page's tools, so the sentence stays one for both arms. The agent is not given the `ayme` server and nothing is filtered: over WebMCP Ayme publishes the screen's Page Object Tools and the read tool `page_objects`, and neither `snapshot` nor its Browser Tools, which the browser tool has its own of. The built-in tools, permission rules, setup message and skill are the browser tool's arm's; `mcp.json` holds the `playwright` entry alone for the MCP arm and no server for the CLI arm.

Set up outside the measured window:

- **The page, served by a server no agent gets.** The setup starts the run's `ayme mcp` with `--webmcp` and opens the start page as [above](#how-ayme-reaches-the-page) (`setUpWebMcpPage` beside `setUpAymePage`, sharing the server start, the browser launch and the wait for the pairing), on the headless system Chrome with a remote-debugging port, and waits until the page publishes the start screen's Page Object Tool through `document.modelContext`. No proxy is written and no socket opened: the server serves the Page Objects and keeps the pairing, and its stdio stays the harness's. The run checks that the server and `@ayme-dev/webmcp`, which the served runtime loads in the page once publication is on, are built, and that the range a page scans is free (the `Ayme MCP server` and `Ayme MCP ports` preconditions, which the Ayme arms share and a suite checks once). The result's `setup` records the server, what it served and that `--webmcp` was on, the pairing, the page's tools as `document.modelContext` listed them, how long after opening the start screen's tool was published (`publishedMs`), under `webmcp` the browser flag and the Page Object Tools among the start screen's tools, and the remote-debugging port.
- **Chrome's WebMCP flag.** The browser is launched with `--enable-features=WebMCP`, as every browser the harness launches is. Playwright supplies no WebMCP API of its own: Playwright MCP and the CLI read `document.modelContext ?? navigator.modelContext` in each frame and collect the tools registered there, and a Chrome without the flag supplies neither. With the flag, Chrome supplies `document.modelContext` natively, with `registerTool`, `getTools`, `executeTool` and `ontoolchange`, and `navigator.modelContext` stays undefined; a tool registered at load and one registered later are both collected. Neither Formbricks nor the init script loads a polyfill. `@ayme-dev/webmcp` publishes to `document.modelContext` alone, the same object, and only once `--webmcp` turns publication on: in every other arm that object lists no tool.
- **Playwright MCP's collection.** `playwright-mcp-with-ayme-webmcp` starts Playwright MCP with `--cdp-endpoint` as the arm with Ayme's server does, without `--no-webmcp`. Playwright MCP collects the page's tools with each snapshot, lists them at the top of the snapshot under `webmcp tools`, and offers each as a tool of its own named `webmcp_<name>`, the dot of a Page Object Tool's name turned into an underscore (`SurveyEditorPage.fillSurveyForm` is `webmcp_SurveyEditorPage_fillSurveyForm`, and `page_objects` is `webmcp_page_objects`), announcing each change of its tool list; so the agent's tool list changes with the screen, as in the arms with Ayme's server. Playwright MCP's `browser_webmcp_list` and `browser_webmcp_call` tools are marked for the CLI alone, where they are `webmcp-list` and `webmcp-call`, and are not offered over MCP.
- **The CLI's handling of page tools.** `playwright-cli-with-ayme-webmcp` starts the session with `attach --cdp` as its twin does, with `PLAYWRIGHT_MCP_WEBMCP=true` in place of `false`. The CLI counts the page's tools in the page status (`N webmcp tools available on the page`), lists them at the top of each snapshot and offers `webmcp-list` and `webmcp-call <name> --params '{...}'`; the agent's own tool list does not change, since every command is a `Bash` call. `webmcp-list` lists what the last snapshot collected: after the page moves to another screen it still lists the earlier screen's tools until a `snapshot` runs.

Counting the page tool calls: `result.json` counts the task turn's tool calls per tool name, and `transcript.jsonl` holds every call with its input, so nothing more is stored. In the MCP arm a call of a page tool is a `mcp__playwright__webmcp_<Class>_<action>` tool call beside Playwright MCP's own `mcp__playwright__browser_*`: `toolCalls.byTool` in `result.json` has the counts, and `grep -o '"name":"mcp__playwright__webmcp_[^"]*"' transcript.jsonl | sort | uniq -c` lists them from the transcript. In the CLI arm every command is a `Bash` call, so count the commands: `jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="tool_use" and .name=="Bash") | .input.command' transcript.jsonl` prints them, and `grep -c 'webmcp-call'` and `grep -o 'webmcp-call [^ ]*' | sort | uniq -c` on that output count the calls and name the tools; `webmcp-list` likewise. The transcript holds no event for a change of the `playwright` server's tool list; the distinct `webmcp_*` tools called and each turn's `system/init` tool list are what it shows of it.

### The Playwright CLI arm

The agent gets the `playwright-cli` command on its `PATH`, the CLI's official skill, the read-only file tools and Bash limited by permission rules to that command. Nothing else: no MCP server, and no other browser interface.

Set up outside the measured window, from the pinned package, with no download:

- **The command.** A one-line `playwright-cli` executable in the run folder's `bin/`, first on the agent's `PATH`.
- **The skill.** The package's `skills/playwright-cli` folder, the one `playwright-cli install --skills` installs, copied into the run's fresh Claude Code configuration folder under `skills/`. That is where Claude Code loads user skills from when its user settings source is on; the folder is empty otherwise, so it loads no skill but this one (Claude Code's own built-in skills stay listed, as for every arm; the permission rules allow only this one). The agent is given read access to the skill folder and the CLI's output folder, and to nothing else outside its working folder.
- **The session.** `playwright-cli open` on the mission's start page, in the profile the harness prepared, on the system Chrome, headless. The CLI names its session after the run, so the plain command reaches it. A restart keeps the profile. The CLI keeps its snapshots and logs in the run's `playwright-output/`. The session is closed after the run.
- **No update check, and no page tools.** The CLI's update check is off, and so is its handling of tools a page registers through WebMCP, as in the published runs. Formbricks registers none.
- **Denied commands.** `npx` (the skill pre-approves `npx playwright`, which would run the lab app's own Playwright), `playwright-cli install` and `install-browser`, and `playwright-cli kill-all`, which kills every Playwright daemon on the machine.

### The agent-browser arms

`agent-browser` and `agent-browser-with-ayme-webmcp` put [agent-browser](https://www.npmjs.com/package/agent-browser), Vercel's browser automation CLI for agents, beside the Playwright CLI arms: `agent-browser` is the counterpart of `playwright-cli`, and `agent-browser-with-ayme-webmcp` of `playwright-cli-with-ayme-webmcp`. The agent gets the `agent-browser` command on its `PATH`, the package's skill, the read-only file tools and Bash limited by permission rules to that command; no MCP server. The two differ in three things: the twin's page gets the lab app's Page Objects served with `--webmcp`, agent-browser's WebMCP support is on for it, and its interface line adds the one sentence.

Set up outside the measured window, from the pinned package, with no download:

- **The command.** A one-line `agent-browser` executable in the run folder's `bin/`, first on the agent's `PATH`, that runs the package's native binary for the machine, as a global install does. pnpm does not run the package's install script, which only marks that binary executable; the setup does.
- **The skill.** The package's `skills/agent-browser` folder, copied into the run's configuration folder under `skills/` as the Playwright CLI arm's is, with the same setup message. It is a stub that sends the agent to `agent-browser skills get core`, which prints the guides the package ships in `skill-data/`, so the agent reads them through the command, in the setup turn or in the measured one.
- **The page and the session.** For both arms the setup opens the start page on a headless system Chrome it launches itself, with the WebMCP flag and a remote-debugging port. The baseline's page is Formbricks as it is, with no init script and no `ayme mcp`. The twin's is the page of [the arms through WebMCP](#the-arms-with-aymes-page-object-tools-through-webmcp) (`setUpWebMcpPage`: the lab app's Page Objects served with `--webmcp` by a server no agent gets), with the two Chrome features agent-browser's WebMCP support needs of an attached browser, `WebMCPTesting` and `DevToolsWebMCPSupport`, joined into the same `--enable-features` switch. agent-browser never launches a browser: `AGENT_BROWSER_CDP` names the port, so every session attaches to that browser over CDP, one the agent names itself included, and a session that loses it fails instead of launching another. The session is named after the run's random suffix (`AGENT_BROWSER_SESSION`), since agent-browser refuses a socket path over 103 bytes and puts the name in it, and started with `agent-browser get url`, which attaches and adopts the open tab without navigating it; the URL it reports must be the start page. The daemons keep their sockets in a short folder of the run's own, made with `mkdtemp` in the temporary folder (`AGENT_BROWSER_SOCKET_DIR`); after the run `agent-browser close --all` closes every session in it, which detaches without closing the browser, the setup removes the folder and then closes the browser. Screenshots go to the run's `playwright-output/`, and the outdated-Chrome check is off.
- **WebMCP.** `agent-browser` runs with `AGENT_BROWSER_NO_WEBMCP=1` and denies `agent-browser webmcp`, as in the published runs, when the lab app shipped Ayme's tools and the variable alone left `webmcp list` and `webmcp invoke` reaching them. Its page now registers no tool. `agent-browser-with-ayme-webmcp` leaves both on. Attached to a page that registered its tools before the session started, agent-browser does not announce them in its output, and after a full page load it reports the catalog cleared; `agent-browser webmcp list` lists them, which is why the interface line names it.
- **Denied commands.** `npx` (the core guide pre-approves `npx agent-browser`), `agent-browser install` and `upgrade`, which download a browser or another agent-browser, `agent-browser doctor --fix`, which reinstalls the browser and purges state, and `agent-browser close --all`, which would close other runs' sessions.

Counting the page tool calls works as for the Playwright CLI arm: every command is a `Bash` call, so list the commands from `transcript.jsonl` with the `jq` filter above, and count `agent-browser webmcp invoke` and `webmcp list` in them.

## The startup lane

Measures only the agent's first turn after loading the skill: whether the skill sends it to the references the task needs, and nothing more. A run costs cents and takes under a minute. It needs Claude Code and the token from [the prerequisites](#prerequisites), and no lab app, Docker, browser or key.

From this directory inside `devbox shell`:

```sh
pnpm eval:startup
pnpm eval:startup -- --scenario drive-the-open-page --model sonnet
```

Every run calls the model and costs money. The exit code is `0` for a pass, `1` for a fail and `2` when the run could not complete, as for [a mission](#one-run).

A scenario is data in [`src/scenarios.ts`](src/scenarios.ts): a framing of the task, the references it should lead the agent to read, and optionally references it must not read, references the verdict ignores and tools for a stub server to list. There are no arms.

| Scenario                        | Framing                                                  |
| ------------------------------- | -------------------------------------------------------- |
| `drive-the-open-page`           | Get ready to drive the open, connected page through Ayme |
| `drive-the-open-page-with-goal` | The same, with `goal` among the listed tools             |
| `set-up-ayme`                   | Get ready to set up Ayme in this project                 |
| `design-page-objects`           | Get ready to design page object models for this project  |

An allowed reference counts neither as expected nor as surplus, read or not; the summary still counts it under files read.

A scenario with tools gets a stub of Ayme's MCP server, [`src/stubMcpServer.ts`](src/stubMcpServer.ts), in the run's MCP configuration under the name `ayme`, so the agent sees `mcp__ayme__<tool>` as with the real server. Behind it is no browser and no app. It lists the scenario's tools and nothing else: the server's own `ayme_connect`, `ayme_list_tools` and `ayme_call`, the Browser Tools `snapshot`, `click`, `fill`, `type` and `navigate`, and two Page Object Tools, `SurveyEditorPage.fillSurveyForm` and `SurveyEditorPage.saveAndClose`. `goal` is listed in one drive scenario and not the other, so its route is checked both ways. A call answers that the tool is a stub, but the agent has no permission to make one. A scenario without tools starts no server.

The agent starts on the lab app folder, which every checkout holds, with the [shared isolated configuration](#missions-and-arms). Its one file tool is `Read`, so no reference is seen without counting as read; beside it, it has the `Skill` tool and no MCP server but the stub, and the shipped skill is copied into its configuration folder as for the Ayme arms. That copy is the one place outside the working root it can read. It gets one message: the scenario's framing and the Ayme arms' setup sentence, which names the skill, says to read what it points to, to read no file outside its folder, not to use the browser, and to reply ready. The message names no reference, so routing stays the skill's job.

The verdict is read from the transcript. A run passes when no condition fails, and `failed` names each one that did:

| Condition                | Holds when                                                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `skill-loaded`           | The Skill tool loaded `ayme`.                                                                                                         |
| `expected-files-read`    | The files read, without allowed references, equal the expected set. A surplus read fails, `SKILL.md` or a working-root file included. |
| `no-forbidden-file`      | None of the scenario's forbidden references was read.                                                                                 |
| `nothing-denied`         | Claude Code's result reports no permission denial.                                                                                    |
| `no-browser-or-mcp-tool` | Every tool called is one of the lane's own, which no browser or MCP tool is, the stub's included.                                     |
| `within-setup-timeout`   | The turn ended within the [setup turn's 120 seconds](#what-is-measured).                                                              |

A timed-out turn is a failed run and stores a result without a wall time or tokens. A turn that ends with an error, or an agent that ends without answering, says nothing about routing: the run could not complete, and only the transcript stays. A `Read` that failed or was denied is not a file read.

Under `results/runs/<run id>/`, a run holds `setup-prompt.txt`, the message as sent; `mcp.json`, the stub with its tools or an empty MCP server list; `transcript.jsonl`; `stderr.log`; and `result.json`, printed when the run ends: `pass`, `failed` and the measures, `wallTimeMs`, `tokens` and `filesRead`, with what a rerun must match. The configuration folder is deleted afterwards.

### A startup suite

From this directory inside `devbox shell`:

```sh
pnpm eval:startup-suite -- --runs 10
pnpm eval:report -- --publish
```

Options: `--runs` per scenario (default `3`), `--model` (default `haiku`). The suite runs every scenario round-robin (run 1 of each, then run 2), writes its manifest (`suite.json`) after every run, and writes its summary at the end, both under `results/suites/<suite id>/`. Its manifest carries `lane: "startup"`, which is how the report tells it from a mission suite; `pnpm eval:report` takes the newest suite of either kind, or `--suite <suite id>`.

A failed verdict, a timed-out turn included, is a result, and the suite goes on. The first run that cannot complete ends it: the runs stored so far are summarized and the summary says the suite stopped early, with any local path taken out of the error, which the manifest keeps whole. The exit code is `0` when every run completed, whatever their verdicts, and `2` when the suite stopped early. A suite killed mid-way leaves a manifest of the runs it finished, and `pnpm eval:report` summarizes those.

Per scenario the summary shows the passes out of the runs stored, the median, lowest and highest of setup time and tokens (input, cache creation, cache read and output added up; a timed-out run has neither and the cell says how many runs it rests on), and how many runs read each file, allowed references included. A file outside the skill's folder counts under one line, `outside the skill's folder`, so a local path is never published; `result.json` keeps the path. It also records what a rerun must match: the date, the Claude Code version, the model and effort, the Ayme commit and the timeout. The skill is read from the working tree, so the commit pins it only for a clean one.

`--publish` writes the summary, formatted with the repository's Prettier, to `summaries/<date>-startup/`, a folder of its own that no Formbricks summary uses. A second startup summary for the same day replaces the first.
