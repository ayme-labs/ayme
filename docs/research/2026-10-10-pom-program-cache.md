# Decision brief: caching the Page Object compile Program

Facts for the design grill on [the Page Object compile session issue (#646)](https://github.com/ayme-labs/ayme/issues/646): how long a cached TypeScript Program should live, what it is keyed by, which bundler signals drive it, and what [ADR-0006](../adr/0006-separate-pom-compilation-from-live-activation.md) should say about it. Nothing here is decided. Researched 2026-10-10 against TypeScript 6.0.3, Vite 8.3.4, Rollup 4.64.5, unplugin 3.4.0, `@angular/build` 22.2.2 and Next.js 16.4.0. Statements marked _inference_ are reasoning from the cited sources, not something a source says.

## Why this matters

Measured on main on 2026-10-10 inside real `vite build`s ([issue comment](https://github.com/ayme-labs/ayme/issues/646#issuecomment-6098898153)):

- `createPomProgram` costs 1.0 to 1.5 s per Page Object module transform (example-vue: a Program of 755 files). Manifest derivation and the import rewrite, both on the type checker, add 0.4 to 0.6 s. The tsconfig gate and dependency walk are under 50 ms together.
- The plugin is 75 to 85 % of the example-vue build. A prototype that reused one Program across the transforms of a build took example-vue from 12.4 s to 5.3 s and example-react from 5.8 s to 4.1 s, with byte-identical `dist`. Every transform after the first dropped to a few milliseconds, because the type checker belongs to the Program too.

## How the plugin builds Programs today

- Each transform of a candidate module calls `pomProgramDependencies` (tsconfig parse plus an import walk) and then `createPomProgram` (another tsconfig parse plus a fresh `ts.createProgram` on the default host) ([transformPomModule.ts](../../packages/unplugin-ayme/src/transformPomModule.ts), [pomProgram.ts](../../packages/unplugin-ayme/src/pomProgram.ts)).
- The Program's `rootNames` are the tsconfig's `fileNames` plus the module, so every module in the same project gets a Program over the same root files ([pomProgram.ts](../../packages/unplugin-ayme/src/pomProgram.ts), `createPomProgram`).
- The tsconfig is found by `ts.findConfigFile` from the module's directory, or by the `tsconfigPath` option. A solution-style tsconfig (`"files": []` plus `references`) is resolved per module to the referenced project that includes it, falling back to the solution config itself when none does (`projectConfigFor`).
- Three integrations ship: Vite through unplugin ([vite.ts](../../packages/unplugin-ayme/src/vite.ts)), an esbuild plugin for Angular's application builder ([angular.ts](../../packages/unplugin-ayme/src/angular.ts)), and an experimental webpack-style loader for Turbopack ([turbopack-loader.ts](../../packages/unplugin-ayme/src/turbopack-loader.ts)). The package exports no Rollup, webpack, Rspack or plain esbuild entry, so those unplugin targets do not need a design now.
- In Vite dev the plugin already records which modules read each dependency and hard-invalidates them from `watchChange` ([unplugin.ts](../../packages/unplugin-ayme/src/unplugin.ts)). Its `ponytail:` note says an edit to a shared import recompiles every Page Object module that reaches it, one Program each, and names "cache the Program" as one of two upgrades (the other: record only the manifest-relevant inputs). The Angular plugin resets its per-module map in `build.onStart`.
- The root export `createPomCompiler` already returns an object (`{ derivePomManifests }`) that builds a Program per call ([derivePomManifests.ts](../../packages/unplugin-ayme/src/derivePomManifests.ts)). Nothing in the repository outside the package calls it.

## What TypeScript can reuse

**Keeping the same Program object is the big win.** A Program creates its type checker lazily and keeps it: `typeChecker || (typeChecker = createTypeChecker(program))` ([program.ts#L2684-L2685](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L2684-L2685)). Any new Program, even one built from an old one, starts with no checker. That matches the measurement: transforms after the first were cheap because they reused one Program and its checker.

**`oldProgram` reuse depends on the host returning the same `SourceFile` objects.**

- `createProgram` calls `tryReuseStructureFromOldProgram`, which returns `Not`, `SafeModules` or `Completely` ([program.ts#L1743-L1745](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L1743-L1745), [types.ts#L4964-L4968](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/types.ts#L4964-L4968)).
- It is `Not` when the root names differ, in content or order, when options that affect module resolution change, when project references change, or when a previously missing file now exists ([program.ts#L2345-L2381](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L2345-L2381)).
- A file counts as unchanged only by identity: `newSourceFile !== oldSourceFile` ([program.ts#L2390-L2424](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L2390-L2424)). A changed file that keeps its imports and references still allows `Completely`; one whose imports changed drops to `SafeModules` ([#L2444-L2551](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L2444-L2551)).
- The default `ts.createCompilerHost` reads and parses the file on every `getSourceFile` call ([program.ts#L392-L412](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L392-L412)), so with it every file looks changed. _Inference:_ passing `oldProgram` then still saves module resolution when imports are unchanged, but no parsing. The plugin uses this default host today.
- _Inference:_ most of the 755 files are `lib.*.d.ts` and `node_modules` declarations that never change during a dev session. A host that caches parsed `SourceFile`s by path (and version or mtime) saves their parse on every rebuild, whatever the reuse result.

**Three TypeScript-provided ways to get an identity-preserving host:**

| API                                                                | What it gives                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Cost for the plugin                                                                                                                                                                                          |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Own caching `CompilerHost` plus `createProgram({ …, oldProgram })` | Full control; the plugin evicts changed files from its `SourceFile` map                                                                                                                                                                                                                                                                                                                                                                                                                                                | The plugin writes the cache (Angular and unplugin-dts do exactly this, below)                                                                                                                                |
| `createLanguageService` with a `DocumentRegistry`                  | `getProgram()` keeps the same Program while script versions are unchanged ([services.ts#L1810-L1815](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/services/services.ts#L1810-L1815)), else rebuilds with `oldProgram` ([#L1822-L1830](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/services/services.ts#L1822-L1830)) and reparses changed files incrementally ([documentRegistry.ts#L330-L331](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/services/documentRegistry.ts#L330-L331)) | The plugin bumps file versions from bundler events; installs no watchers                                                                                                                                     |
| `createWatchProgram`                                               | A versioned source-file cache built in ([watchPublic.ts#L758-L797](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/watchPublic.ts#L758-L797))                                                                                                                                                                                                                                                                                                                                                         | Installs its own file watchers and debounces rebuilds by 250 ms ([#L878-L891](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/watchPublic.ts#L878-L891)), duplicating the bundler's watcher |

Builder programs (`createSemanticDiagnosticsBuilderProgram` and the emit variant) cache diagnostics and emit for affected files ([builderPublic.ts#L136-L235](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/builderPublic.ts#L136-L235)). The plugin uses neither, and they do not carry a checker across Programs.

**TypeScript 7 has no JavaScript API.** "While TypeScript 7.0 is here, it does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API"; `@typescript/typescript6` re-exports the 6.0 API for tools that need it ([Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). The `typescript@7.0.2` package exports only `.` (a version module), `./package.json` and `./unstable/*` entries ([npm registry](https://registry.npmjs.org/typescript/7.0.2)). The plugin depends on `typescript@^6.0.3`, so it keeps resolving the 6.0 API. _Inference:_ whatever caches the Program is also the one place that would change when the plugin moves to the 7.1 API.

Two Turbopack facts matter for any in-memory cache. Loaders run in a pool of reused Node processes that can run concurrently ([process_pool/mod.rs#L606-L632](https://github.com/vercel/next.js/blob/v16.4.0/turbopack/crates/turbopack-node/src/process_pool/mod.rs#L606-L632)), and the pool can be scaled down to zero ([#L859-L870](https://github.com/vercel/next.js/blob/v16.4.0/turbopack/crates/turbopack-node/src/process_pool/mod.rs#L859-L870)). _Inference:_ a module-level cache there lives per worker, can be duplicated or dropped at any time, and has to check its own freshness (mtime or content hash of the Program's files) instead of waiting for change events.

Vite clears its own tsconfig cache and full-reloads the page when a `tsconfig.json` changes ([esbuild.ts#L477-L509](https://github.com/vitejs/vite/blob/v8.3.4/packages/vite/src/node/plugins/esbuild.ts#L477-L509)).

## Keying per tsconfig project

- `ts.findConfigFile` walks up and returns the first `tsconfig.json`, which may be solution-style ([program.ts#L328-L333](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/program.ts#L328-L333)). Editors then follow its references to the project that owns the file ([TypeScript 3.9 release notes](https://github.com/microsoft/TypeScript-Website/blob/v2/packages/documentation/copy/en/release-notes/TypeScript%203.9.md#support-for-solution-style-tsconfigjson-files)). The plugin already does this per module; none of the plugins above does.
- Vite resolves "the closest parent `tsconfig.json` that matches each file", following references, and discourages a fixed `tsconfig` because it "overrides Vite's per-file tsconfig discovery" ([features.md#L56](https://github.com/vitejs/vite/blob/v8.3.4/docs/guide/features.md#L56), [shared-options.md#L647-L656](https://github.com/vitejs/vite/blob/v8.3.4/docs/config/shared-options.md#L647-L656)).
- `parseJsonConfigFileContent` and `getParsedCommandLineOfConfigFile` accept an `extendedConfigCache` shared across parses ([commandLineParser.ts#L2231-L2260](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/commandLineParser.ts#L2231-L2260)).
- _Inference:_ the natural key is the resolved project's tsconfig path, after following a solution-style config to its reference. Every module of one project then shares one Program, whose `rootNames` stay identical across transforms, which `oldProgram` reuse needs. A module outside its project's `fileNames` changes the root names; the plugin adds it today, and a cache would either rebuild for it or keep a separate entry.

## Questions for the grill, with what the facts say

1. **Lifetime in a production build.** One Program per project from the first transform to `buildEnd` (Vite build) or esbuild `onEnd` (Angular one-shot builds) is what the prototype measured. Nothing changes during a build, so no invalidation is needed. Dropping it at the end follows @rollup/plugin-typescript's memory-leak fix.
2. **Lifetime in a dev server: invalidate from the dependency set, or rebuild on any watched change?**
   - _A. Drop on any change in the Program's files._ The plugin already gets `watchChange` for every file it reported through `addWatchFile`. That set comes from `pomProgramDependencies`: tsconfig inputs, the project's root files and transitive _local_ imports. It skips `node_modules` and `lib` declarations, so a dependency upgrade during a dev session would not drop a cached Program; option A needs those inputs too, or a restart rule for them. On a hit, drop that project's Program; the next transform builds one. _Inference:_ that is one rebuild per edit instead of one per affected Page Object module, which covers the `ponytail:` note's case. Each rebuild still pays the full 1.0 to 1.5 s on the default host.
   - _B. A also, plus a caching host and `oldProgram`._ Keep parsed `SourceFile`s across rebuilds and evict only changed files, as Angular and unplugin-dts do. The rebuild skips re-parsing `lib` and `node_modules` declarations; the checker still starts fresh (the checker-bound work measured 0.4 to 0.6 s per module). Create, delete and tsconfig changes rebuild fresh, as unplugin-dts does.
   - _C. A LanguageService per project_, versions bumped from `watchChange`. TypeScript keeps the same Program while nothing changed and handles the reuse; the cost is a different API surface from today's `createProgram`.
   - TypeScript's watch API is the outlier: it would duplicate the bundler's watcher and add a 250 ms debounce in front of a transform that is waiting for it.
3. **Angular rebuilds have no changed-file list.** The options are to keep today's behaviour and start fresh in every `onStart` (correct, no dev speed-up beyond the per-build cache), or check mtimes of the Program's files in `onStart` and evict what changed.
4. **Turbopack has no hooks and pooled workers.** Either leave the loader uncached (it is experimental), or cache per worker with an mtime or hash check on every call.
5. **Key.** The resolved project's tsconfig path (after solution-style resolution) plus the "no tsconfig" case, which `importsPomModule` tolerates and `createPomProgram` rejects today. Whether a tsconfig change rebuilds the project's Program fresh (unplugin-dts, fork-ts-checker, Vite all do).
6. **Where the cache lives.** Inside the compile session the issue proposes, owned by the adapter instance (one per Vite plugin, one per esbuild `setup`), or behind the public `createPomCompiler`, which is already an object and so could hold it. Changing what `createPomCompiler` promises is a public API change.
7. **Memory.** One Program per project per plugin instance, and the plugin already skips SSR transforms. _Inference:_ one or two live Programs in a typical app; the measured Program held 755 files.

## Note for ADR-0006

ADR-0006 separates compiler derivation from bundler transport and runtime activation, and says bundler adapters "can share compiler logic without defining the runtime lifecycle". A cache gives compiler derivation state that outlives one module, and only the bundler knows when a build starts, ends, or a file changes. A consequence along these lines would keep the split:

> Compiler derivation may keep state across the modules of one build, such as a TypeScript Program per project. Bundler adapters own that state's lifetime: they tell the compiler when a build starts and ends and which files changed, and the compiler never watches the file system itself. Where a bundler gives no such signal, the compiler checks its own inputs before reusing state.

Whether this is an amendment to ADR-0006 or a new ADR that cites it is for the grill.
