# Node-side liveness of Page Object Tools: research and pilot (2026-10-06)

Question (Abel): make Page Object Tool liveness "truly work across both Playwright and playwright-lite, in the browser and in Node". Today the browser runtime publishes a Page Object Tool only while its Page Object is live; the e2e adapter prototype publishes every top-level class from the plugin's manifests, so a tool can be offered while its UI is not on the page (results-multi-act.md:45 shows the agent coping: it tapped "Mount counter" before `CounterPage_increment`).

Read: the Ayme clone at /home/claude/ayme (main), the playwright-lite clone, GLOSSARY.md, AGENTS.md, ADR-0004/0006/0007/0009/0019/0020/0025/0029/0030/0031/0032, docs/guide, the example apps, PR #500's two skill references at refs/pull/500/head, and this folder's notes. Vocabulary from the codebase-design skill: module, interface, implementation, adapter, seam, depth. Everything below is a reading of the code unless marked inference. Nothing was committed; the pilot lives in a scratch copy.

## Summary

- The liveness definition already exists as one self-contained in-page function: the `locator.evaluate` callback of `probePomRootState` (packages/ayme/src/pomReachability.ts:16-496). The registry gates tools on its answer (registry.ts:431-455). ADR-0020 requires that callback to be self-contained and serializable, which is exactly what lets Node reuse it.
- The root convention is settled and documented: a `root` locator member is the Page Object Root (docs/guide/guides/page-object-models.md:71-73; GLOSSARY.md:34-41; PR #500 page-object-design.md "Root a POM at what its actions touch"). The examples follow it for every child class (5 of 5) and for none of the registered top-level classes (0 of 10), which rely on registration (component mount) instead.
- Pilot: the callback, copied verbatim, answered "which top-level Page Object Tools are live" from Node over Playwright (one `page.evaluate` per check, 8-12 ms for five classes, 21 ms for twenty), through playwright-lite's own `page.evaluate` inside the page, and as a direct call; the three agreed in every scenario, and against the real example-react app the Node answer matched the browser runtime's published set wherever the class has a root. Rootless classes are the one gap, and it is a policy question, not a code one.
- Effort: medium. The code is small; the decisions (entry point, rootless policy, children, which ADR owns it) are the work.

## 1. How the browser runtime decides a Page Object Tool is live

Registration ties a Page Object to a component's lifetime. `ayme.pom.register(model)` counts registrations and registers the class with the registry when the count goes from 0 to 1; `unregister` disposes at 0 (packages/ayme/src/runtime.ts:362-379). The framework adapters call these from the component's effect or scope (packages/react/src/index.ts:96-99; packages/vue/src/index.ts:169-170). Registering adds an `ObservedRegisteredPom` and starts the page observer when the registry was empty (registry.ts:186-228); disposal removes it and stops observing when empty (registry.ts:222-226). Contract row C6 in docs/framework-integrations.md says the same.

Observation. One `MutationObserver` on `document.documentElement` plus scroll, resize, transition and animation events schedule a coalesced probe on a 0 ms timer (registry.ts:96-103, 230-264). A probe walks every registration: if the manifest declares a `root` locator member, it reads the instance's `root` and observes it (registry.ts:804-822, 833-855); it then counts every locator member and recurses into Page Object Children, observing each child's `root` (registry.ts:905-984). Only changed observations notify subscribers (registry.ts:299-327).

The definition of present and available. `probePomRootState(locator)` (pomReachability.ts:10-500): a root with `count() !== 1` or `!isVisible()` is absent (lines 14-15); otherwise one `locator.evaluate` runs the self-contained callback (lines 16-496). It returns absent for a disconnected element (339-342); marks the root blocked when an open `:modal` exists that neither contains nor is contained by it, or when it or an ancestor is `inert`, with a modal escaping inherited inertness (343-368); projects the root's client rects through its scroll ancestors for four scroll alignments, clipping to each scroll port, `clip-path` insets and the viewport (370-489); sets `present` when any projection leaves a rectangle (490); and sets `available` when the root is not blocked and one of nine sample points hits the root itself or something inside it, after discounting projected sibling occluders (491, 304-337). Any error means absent (497-499). It never scrolls, clicks or focuses (ADR-0019, ADR-0020). An observed root also has to resolve to the same element before and after the probe (registry.ts:839-853).

Gating. `listCallerAwarePomTools` (registry.ts:431-455): a class "declares a root" when its manifest has a locator member named `root` (434-436). A top-level tool is active when the class declares no root, or when its root observation is present, connected and available (439-444, 383-393). A child's tool is active only when the child's root is available (445-449). Collections publish one tool for all items and act on a Structural Ref of the item's root (598-649).

What agents see. `resolvePublishedTools` composes `snapshot`, Browser Tools, Custom Tools, the live Page Object Tools and `goal` (publishedTools.ts:47-83). The runtime object recomputes `ayme.tools.list()` on every registry change (runtime.ts:237-244, 411). WebMCP publication mirrors the same set: it probes, subscribes, and on each change withdraws registrations that left the set and registers new ones (webMcp.ts:117-120, 203-255, 259-264); after each agent call it re-probes before answering (176-181). The Agent Connection pushes `tools.list()` to the Node MCP server on open and on every change (packages/mcp/src/tools/application/pageToolBehaviours.ts:5-19; the server stores them at packages/mcp/src/connection/application/agentConnection.ts:66), the server announces `notifications/tools/list_changed` (packages/mcp/src/tools/infrastructure/mcpToolServer.ts:22,42) and keeps `ayme_list_tools` as a fallback (listToolsTool.ts:12-20). The consumer doc states the rule in one sentence (docs/guide/guides/publish-tools.md:45).

So Node already receives a liveness answer today, but only by mirroring the browser runtime over the Agent Connection. Nothing in Node computes it.

## 2. What the plugin derives from a class

`derivePomManifests(file)` (packages/unplugin-ayme/src/derivePomManifests.ts:35-80; exported at src/index.ts:441) returns one `PomManifest` per `@ayme` class in the file: `className`, optional `description`, `members`, `components`, `tools` (packages/ayme/src/contracts.ts:72-78). A member is recorded when it is a public field, getter or parameterless method whose type is `Locator` (by symbol name, derivePomManifests.ts:436-439) or a Page Object Model, with only `memberName`, `kind` ("locator" or "component"), `access` and, for components, the class name and whether it is a collection (contracts.ts:30-45; derivePomManifests.ts:82-156). A private or protected `root` is still recorded (393-411), so inherited base-class roots count. Tools carry method name, tool name, descriptions, JSON input schema and parameter list (219-261). `transformPomModule` injects `registerCompiledPom(Class, manifest)` into the module, imported from `@ayme-dev/ayme/internal` (transformPomModule.ts:38-43). A spec already calls `derivePomManifests` from Node (apps/example-vue/tests/vue-webmcp.spec.ts:7,170).

What the manifest does not know: the locator's selector or expression (a Locator is built in the constructor, so only an instance has it), which component registers the class or whether anything does, and anything about the DOM. It knows that a `root` is declared, not where it points. A Node consumer therefore needs the class itself, constructed with its Page, to read `instance.root`; the decorators are runtime no-ops (packages/ayme/src/decorators.ts:1-2, 35-62), so the classes run unchanged in Node.

## 3. The root convention in examples, docs, skills and tests

Documented rule: "A `root` locator member is the model's Page Object Root ... A child's tools are live only while its root is on the page and available, so a child needs a `root`. A registered top-level model without one has tools that are live as long as it is registered." (docs/guide/guides/page-object-models.md:71-73). PR #500's page-object-design.md adds: a POM's `root` must contain every element its actions touch; portaled menus and dialogs get their own POM rooted at the content, held as a Page Object Child and returned from the opening action; controls stay named locators; prefer test ids; its example roots even a page-level POM (`this.root = page.getByTestId("profile-menu")`). Its runtime-integration.md: top-level POMs are registered with `usePageObject`/`injectPageObject` in the component that owns their lifetime; children are discovered recursively; a POM only returned from an action is never registered, so its tools are never live; `ayme.tools.list()` lists live tools.

What the code does: child classes, 5 of 5 with a root, always as a public `readonly root: Locator` field declared first and set from a `Locator` constructor argument: apps/example-vue/playwright/pom/ListItem.ts:7,12-16 and ArchiveDialog.ts:6,9-10; apps/inspector-fixture/pom/ListItem.ts:7,9-11, TodoPage.ts:37,40-42 (TodoItem) and :52,56-58 (ArchiveDialog). Registered top-level classes, 0 of 10 with a root, constructed from `Page` with page-wide locators: apps/example-react/playwright/pom/CounterPage.ts:5-12, example-vue ListPage.ts:6-21, example-sveltekit/src/lib/pom/CounterPage.ts, example-angular CounterPage.ts and OtherPage.ts, example-next CounterPage.ts, example-nuxt CounterPage.ts, inspector-fixture ListPage.ts and TodoPage.ts:11-22, mcp-fixture/app/Basket.ts:9-14. The compiler fixtures test private and protected roots on a base class (packages/unplugin-ayme/src/fixtures/privateRootPom.ts, protectedRootPom.ts). The runtime tests spell the rule out: "gates rooted page actions and preserves rootless actions" (packages/ayme/src/pomAvailability.browser.test.ts:174) and the reachability scenarios (pomReachability.browser.test.ts:19-305). No decorator option, constructor convention or "first locator" rule exists for a root; the name `root` is the whole convention, recognised by name in the compiler (derivePomManifests.ts:393-411) and the registry (registry.ts:434-436, 812-814).

Consistency: complete for children, consistently absent for top-level classes. That absence is by design in the examples (they lean on mount), and PR #500 moves the convention towards a root on every POM. feature-backlog.md:58-60 records the prototype adding roots to the example-react classes.

## 4. Node-side design

A deep module, named after the glossary: Page Object Availability.

Interface (the facts a caller must know):

```ts
// @ayme-dev/ayme, a Node-safe entry (see placement). The one definition.
type PomRootState = { present: boolean; available: boolean };
/** In-page and self-contained: no closure, no imports, serializable in and out. */
function observePomRoots(roots: (Element | null)[]): PomRootState[];
/** Any Playwright-compatible Page. Each root must match exactly one element, else absent.
 *  One evaluation of observePomRoots per call. Never scrolls, clicks or focuses. */
function observeRootStates(page: Page, roots: readonly Locator[]):
  Promise<(PomRootState & { matches: number })[]>;

// @ayme-dev/e2e (first Node consumer), the fold over manifests:
function livePageObjectTools(page: Page,
  registrations: readonly { manifest: PomManifest; instance: object }[],
  options?: { rootless: "live" | "omit" | "error" }
): Promise<{ tools: ToolManifest[]; poms: PomLiveness[] }>;
```

What it hides: the ambiguity rule, Playwright's visibility rule, modal and inert blocking, scroll projection, clipping, occlusion sampling, handle disposal, and whether the Page is Playwright or playwright-lite. The deletion test holds: remove it and every consumer (registry, WebMCP, Agent Connection, e2e adapter) grows its own copy of ADR-0019/0020.

The seam is the Playwright `Page`/`Locator` interface, as ADR-0019 already decided ("evaluated through the standard Playwright Locator interface; the browser adapter contract is not extended"). Two adapters satisfy it, Playwright in Node and playwright-lite in the page, so the seam is real, not hypothetical. The browser registry calls the definition directly or through `locator.evaluate` (today's path, pomReachability.ts:16); Node calls it through `page.evaluate` with element handles resolved in parallel from each root's `elementHandles()`. Playwright cannot resolve a Locator inside the page without a handle, so "one evaluation per check" means N parallel handle resolutions plus one evaluation, not one round trip. The pilot measured both parts.

Can both sides share one definition? Yes, and they should: the callback is already written to ADR-0020's rule ("The evaluate callback must be self-contained and return serializable state"), and the pilot ran lines 17-495 unchanged in three ways. The one change for parity: move the prelude (`count() !== 1 || !isVisible()`, pomReachability.ts:14) into the definition, so that Node does not pay two more calls per root. The pilot ported Playwright's visibility rule for that (inference; it must be checked against the pinned InjectedScript).

Placement, following the repo's rules. The definition belongs in `@ayme-dev/ayme`, tag `core` (packages/ayme/turbo.json:3; ADR-0004), where `pomReachability.ts` lives and whose only import is a type (pomReachability.ts:1). It needs an entry Node can import without the browser modules: the package's `.` and `/internal` entries pull in `browserPage` and playwright-lite (packages/ayme/src/index.ts:3; internal.ts:49), and `/server` is the Decision Endpoint (server.ts). ADR-0025 anticipated this: "The registry read model ... becomes a public interface when a second adapter reads it, such as a driver on the Playwright side; its shape is designed against that caller". The manifest fold and the rootless policy belong to the first Node consumer, the `@ayme-dev/e2e` package (tag `adapter`, designed in feature-backlog.md "Packaging and store"), which already has the classes and the manifests. The plugin stays as it is (ADR-0006). The MCP package keeps mirroring the browser's answer; it should not compute one.

Rootless top-level classes. The browser says: live while registered (registry.ts:439-441; docs page-object-models.md:73). Node has no registration signal; it only has "declared in the manifests". Three policies: `live` (today's prototype: declared means registered; over-offers, the agent coped in results-multi-act.md:45), `omit` (never offer a rootless class from Node; strict, loses tools), `error` (the adapter refuses a rootless class and points at PR #500's rule). Recommendation, for the grilling: default `error` in `@ayme-dev/e2e` with `live` as an explicit opt-in, and give the example classes roots as the backlog already plans. A heuristic such as "every locator member matches" (ADR-0009's superseded DOM-match rule) would diverge from the browser and is not recommended.

What the design does not cover yet: Page Object Children and collections. The registry reaches them by reading members on the instance, including calling `items()` (registry.ts:905-984), and collection tools take a Structural Ref (598-649), which does not exist in Node. Top-level classes are enough for the e2e adapter's current scope.

## 5. Pilot

Code in the scratch directory `liveness/pilot/` (not in the shared folder): `inPage.ts` is generated from pomReachability.ts lines 17-495 unchanged, wrapped as an n-ary function with the visibility port; `probe.ts` is the module above; `poms.ts` holds five classes and hand-written manifests in `derivePomManifests` shape; `fixture.html` mimics example-react (counter section, projects section, off-canvas sidebar, modal dialog, a rootless status class); `run-fixture.ts`, `run-lite.ts`, `run-app.ts` are the three runs. Browser: the container's Chromium 1194 driven by the repo's Playwright 1.62.1 (installed into a scratch copy of the repo with `pnpm install --filter "@ayme-dev/example-react..."`, 27 s, which also built the playwright-lite fork at cd4217e9); `turbo run build` of the six dependencies took 15 s; example-react ran on its Vite dev server with `--mode inspector-disabled`.

Fixture results (five classes, seven repeats, medians): initial, Counter and Projects available, Sidebar present=false (off-canvas), ArchiveDialog absent (0 matches), StatusPage "no root: live while registered"; after unmounting the counter, Counter has 0 matches; with the modal open, Counter and Projects present but unavailable, ArchiveDialog available; with the sidebar open, Sidebar available and the partly covered sections still available. Cost per check: resolve handles 5-9 ms + one evaluate 3-4 ms (0.2-0.6 ms inside the page) = 8-12 ms; twenty registrations: 15 + 6 ms = 21 ms. A sequential variant in the browser runtime's shape (count, isVisible, evaluate per root) took 28-46 ms for five and 150 ms for twenty.

playwright-lite (fork dist loaded as an ES module into the fixture page): the same function through the lite Page's `elementHandles()` + `evaluate` and as a direct call with the fork's `resolveLocatorElements` (its `/internal` entry) gave the same present/available as Node's Playwright answer for all four roots in all three scenarios; 2-15 ms via lite evaluate, 1-3 ms direct.

Real app (apps/example-react, browser answer read through the recording WebMCP driver of `@ayme-dev/ayme/testing`): mounted, both publish `CounterPage.increment`; after "Unmount counter" the runtime withdraws it and the Node probe with a rooted copy of CounterPage reports 0 matches; after "Mount counter" both have it back; with a modal injected over the page the runtime still publishes it (the shipped class has no root, so registration drives it) while the rooted Node copy says present but unavailable; the manifest without a root makes Node say "declared = live" throughout. Node cost on the real page: 9-12 ms per check after the first (60 ms, warm-up).

What did not run: nothing failed. The only approximation is the visibility port (inference above).

## 6. Open questions for the grilling with Abel

1. Rootless top-level classes in Node: `error`, `omit` or `live` by default? Should "a POM needs a root" become a compiler diagnostic once PR #500 lands, which would also change the browser's behaviour for consumers' rootless classes?
2. Entry point: a new Node-safe entry of `@ayme-dev/ayme` for the definition, or does only `@ayme-dev/e2e` import it? ADR-0019/0020 say "keep this policy in WebMCP"; sharing it with Node needs an ADR clarification or a new ADR (AGENTS.md requires presenting it first).
3. Visibility parity: port Playwright's rule into the definition (one evaluation, risk of drift across Playwright versions) or keep `isVisible()` calls (N more round trips)?
4. Children and collections in Node: needed now? Collection tools are addressed by Structural Ref, which Node lacks; what addresses an item in e2e?
5. When does e2e probe: once per act before offering tools (10-20 ms), or on demand? Is a re-probe after e2e's own clicks needed?
6. Alternative for apps that run Ayme: ask the browser runtime instead (the Agent Connection already mirrors `tools.list()`; `@ayme-dev/mcp/testing` pairs a Playwright page). Exact agreement, but then the tool runs in the page on playwright-lite, not on e2e's Playwright page. Is that acceptable for e2e's recording?
7. Root authoring guidance for e2e users: exactly one match is required; test ids over text (PR #500). Does the adapter report ambiguous roots as diagnostics?

## 7. Effort estimate

Medium. Small code: extract the callback into an n-ary pure function with the prelude inside, have the registry call it, add the Node-facing function and entry, write the e2e fold (the pilot's probe is about 100 lines). The work is in the decisions above, the parity tests (the reachability scenarios in pomReachability.browser.test.ts should run through both adapters), the visibility port check against the pinned InjectedScript, the ADR and glossary touches with their approval steps, and the example apps' roots. Large only if children and collections must work in Node at the same time.
