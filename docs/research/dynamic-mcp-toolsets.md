# Dynamic MCP toolsets: visibility, effectiveness and cost

Research for #245 "Research: evaluate dynamic MCP toolsets for agent effectiveness and efficiency". Question: when is exposing a changing set of tools (tools that appear while a page or component instance exists and disappear when it goes away) a good design for agents, and when should a system prefer stable parameterized tools or tool search with deferred loading?

Sources were read on 2026-10-02. GitHub links name the commit that was read. Each claim is labelled:

- **spec**: normative text of a released MCP revision.
- **draft**: a Community Group draft, an open proposal, or an issue thread in a standards repo.
- **docs**: a vendor's own product or API documentation.
- **source**: shipping client code, read at the cited commit. This is observed implementation behaviour, not a guarantee.
- **measured**: a published measurement or first-party experiment.
- **inference**: my reasoning from the above. Not verified.

## Recommendation

Dynamic per-instance tools are not a good default for Ayme's MCP leg (a relay that exposes page tools to desktop MCP clients). They are acceptable, with limits, for the WebMCP leg (agents built into or attached to the browser), at coarse route or view granularity.

1. **Prefer a stable, parameterized tool per action kind, with an explicit instance handle as an argument.** The current MCP revision says `tools/list` "MUST NOT vary per-connection or as a side effect of other requests" (F2), and its own guidance for cross-call state is server-minted handles passed as ordinary arguments, with expiry reported as a recoverable tool execution error (F3). Playwright MCP, the closest browser precedent, works this way: a fixed tool set and an element `ref` taken from the latest snapshot (F20).
2. **Keep the model-visible set small with discovery, not churn.** Every measurement found shows that fewer, relevant tool definitions in context improve selection and cut tokens (F14 to F17). Tool search with deferred loading achieves that without invalidating the prompt cache (F11). Changing the upfront tool list invalidates the whole cache on the Claude API (F10) and breaks the cache on OpenAI (F12).
3. **Use dynamic registration only where the agent is in the page.** Chrome's own guidance is to register tools only while useful for the current page state (F7), and browser agents re-observe the page on a settle heuristic rather than on every `toolchange` (F8). Register by route or view, keep the set under Lighthouse's 40-tool warning (F7), and do not treat absence as an explanation: keep a stable state tool that reports what is unavailable and why (F9).
4. **Never use registration as the authorization check.** Every call must re-check that its target instance still exists, because discovery and invocation can race in every client surveyed (F6, F9).

Whether "only currently available tools are visible" improves agent behaviour more than a stable tool that reports "this instance is gone" is **not measured anywhere I found**. It remains a hypothesis (see §2 and the experiments at the end).

## Facts

1. The current MCP revision is `2026-07-28`. Servers that declare `tools.listChanged` "SHOULD send" `notifications/tools/list_changed`, and only to clients that opened a `subscriptions/listen` stream with `toolsListChanged: true` ([2026-07-28 tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#list-changed-notification)). In `2025-11-25` the notification needed no subscription ([2025-11-25 tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#list-changed-notification)). Neither revision says when a client must re-fetch or when the model must see the change. Authority: spec.
2. `2026-07-28` adds: servers "**MUST** respond to `tools/list` requests with the set of tools currently available … This set **MAY** be empty and **MAY** change over time …, but **MUST NOT** vary per-connection or as a side effect of other requests on the connection" ([tools, Capabilities](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#capabilities)). The SEP behind it states the intent as "`tools/list` / `resources/list` / `prompts/list` MUST NOT depend on per-connection or prior-tool-call state" ([SEP-2567, merged 2026-05-07](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2567)). Authority: spec.
3. The same revision gives non-normative "Stateful Tools" guidance: return "an explicit handle from a creation tool and accept that handle as an argument on subsequent calls"; handles should be opaque; "A call against an expired or unknown handle should return a tool execution error that says so, so the model can recover" ([tools, Stateful Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#stateful-tools)). Authority: spec (non-normative section).
4. `2026-07-28` requires `ttlMs` and `cacheScope` on `tools/list` results. A `list_changed` notification "invalidates the cached response" ([caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching#interaction-with-notifications)). Servers "**SHOULD** return tools in a deterministic order", which "improves LLM prompt cache hit rates when tools are included in model context" ([tools, Capabilities](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#capabilities)). Authority: spec.
5. Calling an unknown tool is a protocol error (JSON-RPC `-32602`), which clients only "**MAY**" pass to the model; tool execution errors (`isError: true`) "**SHOULD**" be passed to it ([tools, Error Handling](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling)). Authority: spec.
6. WebMCP (Draft CG Report, 30 September 2026): tools are unregistered by aborting the `AbortSignal` passed to `registerTool`; names are unique per `ModelContext` (duplicate registration rejects with `InvalidStateError`); each change fires `toolchange` at the document's `ModelContext`; if an execution targets a tool no longer in the map, it completes with failure ([WebMCP draft](https://webmachinelearning.github.io/webmcp/)). How a browser agent observes tools is implementation-defined. Chrome 153 does not interrupt in-flight executions on unregistration ([Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api), updated 2026-09-21). Authority: draft; docs.
7. Chrome's Lighthouse audit "issues a warning when more than 40 tools are registered" and advises: "Register tools only when they're useful for the current page state, and unregister them when they're no longer needed" ([Registered WebMCP tools](https://developer.chrome.com/docs/lighthouse/agentic-browsing/registered-webmcp-tools), updated 2026-09-21). Authority: docs.
8. A WebMCP editor reports that agents decide when a page has "settled" before taking a page observation that includes the tool list, that this observation "is unlikely to take place on _every_ `toolchange` event", and that an observation can therefore capture a partial tool set during hydration or SPA navigation ([webmcp#328](https://github.com/webmachinelearning/webmcp/issues/328), open, 2026-09-29). Microsoft's WebMCP contact confirms "we do not know when tools are available, and we have to guess when a page will be ready" (same thread, 2026-10-01). Authority: draft (issue thread).
9. [webmcp#262](https://github.com/webmachinelearning/webmcp/issues/262) (open) documents that unregistering a tool reduces the reason to "tool no longer exists". Implementers report working around it with a stable read tool that lists unavailable tools with `because` and `how`, and agree that "discovery state is guidance, not authorization". [webmcp#306](https://github.com/webmachinelearning/webmcp/issues/306) reports that `keep-alive` component caching stops unmount hooks from firing, so mount-driven tools accumulate. [webmcp#255](https://github.com/webmachinelearning/webmcp/issues/255) reports agents "failing to re-find the relevant tools" after tools re-register across a navigation. Authority: draft (practitioner reports, not measurements).
10. Claude API prompt caching follows `tools → system → messages`; "Modifying tool definitions" invalidates the "Entire cache (tools, system, messages)" ([tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)). Authority: docs.
11. Claude API tool search: deferred tools are excluded from the prefix, discovered tools are appended inline as `tool_reference` blocks, and "adding tools dynamically through tool search does not break your cache". Every deferred definition must still be sent on every request. A `tool_reference` to a tool missing from `tools` returns a 400, "Tool reference 'unknown_tool' not found in available tools". References are expanded "throughout the conversation history". Limits: 10,000 deferred tools, 5 results per search by default. Recommended at 10+ tools or 10k+ tokens of definitions ([tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Authority: docs.
12. OpenAI: function definitions "are injected into the system message … and are billed as input tokens"; "Aim for fewer than 20 functions available at the start of a turn" (a "soft suggestion"); use `allowed_tools` to restrict tools while keeping the cache ([function calling](https://developers.openai.com/api/docs/guides/function-calling)). Tool search (`gpt-5.4` and later) loads tools "at the end of the model's context window" to preserve the cache, but "changing the loaded tool set will break the model's cache" ([tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)). Authority: docs.
13. OpenAI's Responses API MCP tool emits an `mcp_list_tools` item and "will not fetch a list of tools from the MCP server again at each turn" while that item stays in context. `list_changed` is not mentioned ([MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)). Authority: docs.
14. Anthropic: tool definitions for a five-server setup take "~55K tokens"; tool search reduced ~77K to ~8.7K tokens (85%); on Anthropic's MCP evaluations accuracy rose from 49% to 74% (Opus 4) and from 79.5% to 88.1% (Opus 4.5). The most common failures were "wrong tool selection and incorrect parameters", especially with similar names ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use), 2025-11-24). The API docs add that selection accuracy "degrades once you exceed 30–50 available tools" ([tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). Authority: measured (first-party).
15. RAG-MCP: retrieving relevant tools before selection "more than triples tool selection accuracy (43.13% vs 13.62% baseline)" and cuts prompt tokens by over 50% on an MCP stress test ([arXiv:2505.03275](https://arxiv.org/abs/2505.03275), v1 2025-05-06). Authority: measured (third-party, single paper).
16. Anthropic's tool-writing guidance: prefer fewer consolidated tools; prefix vs suffix namespacing has measurable, model-dependent effects; resolving opaque UUIDs to meaningful identifiers "significantly improves Claude's precision in retrieval tasks by reducing hallucinations"; errors should be actionable ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents), 2025-09-11). Authority: docs (first-party evaluation, numbers not published).
17. In an origin-trial experiment across Codex, ChatGPT/Chrome, Antigravity and Edge, "Native discovery was irregular": two server-confirmed invocations in five Antigravity attempts, and "no confirmed native invocation" in the observed ChatGPT/Chrome and Edge configurations ([webmcp#256](https://github.com/webmachinelearning/webmcp/issues/256), 2026-08-22). Authority: measured (small, self-reported, not peer-reviewed).
18. GitHub's MCP server shipped `--dynamic-toolsets` (start with meta-tools, enable toolsets on demand via `list_changed`) in April 2025 to fight "tool confusion" ([github-mcp-server#275](https://github.com/github/github-mcp-server/issues/275)). Users then reported it not working in Claude Desktop because the host did not act on tool change notifications (same thread, 2025). GitHub removed the feature on 2026-05-20 as "tech debt cleanup", noting it "was local-only — never offered by the remote server" ([github-mcp-server#2512](https://github.com/github/github-mcp-server/pull/2512)). The removal gives no effectiveness data. Authority: source; docs.
19. Client behaviour on `list_changed`, from docs or source: see the [support table](#client-and-provider-support). Authority: docs; source.
20. Playwright MCP exposes a fixed tool set (extra capabilities only via `--caps` at startup). Element tools take `target`, the "Exact target element reference from the page snapshot, or a unique element selector" ([README at f183dad4](https://github.com/microsoft/playwright-mcp/blob/f183dad4a5/README.md)). Authority: source (docs in repo).

## 1. Visibility and lifecycle

A tool change passes three layers. Each one can drop or delay it.

| Layer                     | MCP                                                                                                                                             | WebMCP                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Server registration       | Server changes its list and sends `list_changed` (SHOULD, only if declared; in `2026-07-28` only on an open `subscriptions/listen` stream) (F1) | Page calls `registerTool` or aborts its signal; browser fires `toolchange` (F6) |
| Client discovery          | Client re-runs `tools/list`. Neither revision says when. TTL caching can delay it further without a notification (F4)                           | Agent re-observes the page on its own settle heuristic, not per event (F8)      |
| Model-visible definitions | Client decides when the next model request carries the new list, or, with tool search, only the names (F19)                                     | Same, inside the browser agent; unspecified                                     |

The protocols guarantee only the first layer, and only as a SHOULD. Everything after that is client behaviour (see the [support table](#client-and-provider-support)).

**The `2026-07-28` constraint.** F2 forbids a list that varies "as a side effect of other requests on the connection", and the SEP phrases it as not depending on "prior-tool-call state". A page-backed relay whose tool list changes because an agent's own tool call opened a dialog or navigated is, on a strict reading, that case. A list that tracks external state (the user navigates the page) is plainly allowed ("MAY change over time"). Ayme cannot always tell which of the two caused a change, so per-instance tools on the MCP leg sit in a grey zone of the current revision. This reading is inference; the spec text and SEP intent are quoted above.

**Notification transport is fragile in practice.** Claude Code on its v2 runtime reopens a closed `subscriptions/listen` stream at most three times if it closes within 10 seconds, and after five reopens in an hour waits about six hours; until then "you keep the server's last fetched tools" (F19, Claude Code row). Before v2.1.214 a failed refresh replaced a server's tools with an empty list. A design whose correctness depends on every notification arriving inherits these limits.

**When a tool disappears between discovery and invocation.**

- MCP: the server answers with an unknown-tool protocol error, which the client may not show the model (F5). Under the current revision a stable tool that rejects a stale handle with `isError: true` is the documented recoverable path (F3).
- WebMCP: the execution completes with failure; Chrome 153 does not interrupt an execution already running (F6).
- Claude API with tool search: if the model already discovered the tool and the client then drops its definition from `tools`, the next request carrying that `tool_reference` in history is rejected with a 400 (F11). A client must either keep sending dead definitions or rewrite history. This is inference from the documented error and the documented history expansion; it is not tested (experiment A).
- What each client shows the model in these cases is undocumented (experiment D).

## 2. Agent effectiveness

**What is measured.** Smaller, relevant tool sets in context improve selection: 49% → 74% and 79.5% → 88.1% with tool search (F14), 13.62% → 43.13% with retrieval (F15), and vendor thresholds of roughly 20 (OpenAI, F12), 30–50 (Anthropic, F14) and 40 (Lighthouse, F7). Similar names are a named failure mode (F14).

**What this does and does not show.** All of these compare a large flat list with a small relevant one. None compares the three approaches in this report. Each approach can produce a small model-visible set:

- dynamic tools, by registering only what exists;
- stable parameterized tools, by having one tool per action kind instead of one per instance;
- tool search, by loading only what the model asks for.

So the measurements support "keep the visible set small", not "make presence track availability".

**Hypotheses with no measurement found.**

- H1: Showing only currently available tools reduces failed calls compared with a stable tool that returns an actionable "instance gone" error. Practitioners report the opposite risk: absence carries no reason, so agents hunt for a remembered tool (F9).
- H2: Per-instance tools help the model tell instances apart. Against it: per-instance names multiply near-identical names, which F14 names as a failure mode.
- H3: Agents notice mid-task tool changes. Against it: browser agents observe on a settle heuristic (F8), notification delivery depends on the client (F19), and an origin-trial experiment found native discovery "irregular" (F17).

**Where dynamic registration does help (practitioner evidence, not measured).** Removing a tool before planning stops an agent from building a plan around a capability a human revoked or a workflow phase has passed; a failed call after the plan is "late" ([webmcp#262](https://github.com/webmachinelearning/webmcp/issues/262), Incident Command comment). This argues for dynamic registration of _capabilities_ that change rarely and at a coarse grain, not of instances.

## 3. Efficiency

Separate two costs.

**Protocol overhead** (between server and client, not billed as model input):

- One `list_changed` notification plus one full `tools/list` re-fetch per change. Without pagination the re-fetch is O(tool count × schema size) bytes (F1, inference).
- With notifications unsupported or a stream down, clients fall back to TTL or never refresh (F4, F19).
- SEP-2567 states that merely allowing per-connection lists "forces `O(subagents × servers)` re-fetches on everyone" (F2). It is the spec authors' argument, not a measurement.
- In WebMCP, registration is an in-page call; its cost is negligible beside the agent's page observation (inference).

**Model-input cost** (billed; dominates):

- Each upfront tool definition is input tokens on every request (F12). Five servers took ~55K tokens in Anthropic's example (F14).
- Changing the upfront list invalidates the entire Claude prompt cache, including the conversation (F10). With tools loaded upfront, every mount or unmount of a per-instance tool is a full cache miss on the next request (inference from F10). This applies to any client that loads MCP tools upfront: Claude Code with tool search off or behind a non-first-party gateway, and any client whose docs or source show no deferral (F19).
- With deferred loading, adding tools does not break the Claude cache (F11), but removing an already-discovered tool hits the 400 in §1. On OpenAI, changing the loaded set breaks the cache (F12).

**What scales with what** (inference from F10 to F14):

| Driver           | Upfront loading                                                            | Tool search / deferral                                                                                         |
| ---------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Tool count       | Linear input tokens on every request; selection accuracy falls past ~20–50 | Names only (Claude Code) or nothing until searched; full definitions still sent in the request, not in context |
| Schema size      | Linear input tokens on every request                                       | Paid once per discovered tool, inline                                                                          |
| Change frequency | One full cache invalidation per change that reaches the request            | Additions free; removals need definition retention or history rewrite                                          |

For many repeated instances (a list of 50 rows, each with its own tools), per-instance tools multiply both count and change frequency. A single parameterized tool keeps both constant.

## 4. Comparison of the three approaches

| Concern                     | Dynamic per-instance tools                                                                                                          | Stable parameterized tool + instance handle                                               | Discovery / search + deferred loading                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Visibility of changes       | Depends on notification delivery and client refresh (F1, F19) and, in the browser, on observation timing (F8). Weakest link decides | Nothing to propagate: the tool set is fixed; instance state is read through a tool result | Additions reach the model when it searches; removals are a problem (F11)                                |
| Spec fit (MCP `2026-07-28`) | Grey zone when changes follow the agent's own calls (F2)                                                                            | The pattern the spec recommends (F3)                                                      | Client-side feature; independent of server list churn                                                   |
| Agent effectiveness         | Small set if instances are few; many near-identical names if many (F14). Absence carries no reason (F9). Benefit unmeasured         | Small set; model must carry the handle. Stale handle returns a recoverable error (F3, F5) | Measured gains over large flat lists (F14, F15); search quality depends on names and descriptions (F11) |
| Efficiency                  | Cache invalidation per change under upfront loading (F10); re-fetch per change                                                      | Constant definitions; cache stable                                                        | Definitions paid only when used; cache preserved on additions (F11)                                     |
| Lifecycle / identity        | Identity is the tool name; remount may reuse or change it; registration accumulates if unmount hooks do not fire (F9)               | Identity is the handle; server decides lifetime and staleness, every call is re-checked   | Inherits the identity scheme of whatever tools it loads                                                 |
| Best fit                    | In-page browser agents, few long-lived capabilities that change with route or permission (F7)                                       | Many repeated instances; frequent component churn; MCP relay to desktop clients           | Large or growing catalogs (10+ tools or 10k+ tokens, F11); combinable with either other approach        |

The approaches are not exclusive. A stable set of parameterized tools, kept small enough to load upfront, with tool search as the client's scaling mechanism, combines the strengths of columns two and three.

## 5. Identity

- **Name per kind, handle per instance.** Tool names should be stable for the life of the server; instance identity belongs in an argument (F3, F20). Names must stay within 1–128 characters of `[A-Za-z0-9_.-]` in both MCP and WebMCP (F6, [2026-07-28 tool names](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool-names)), so encoding instance keys in names is constrained anyway.
- **Opaque but legible.** The spec asks for opaque handles so models do not parse or guess them (F3). Anthropic found meaningful identifiers beat raw UUIDs for retrieval precision (F16). A handle can be opaque in structure and still paired with a human-readable label in the tool result (inference reconciling the two).
- **Lifetime and replacement.** A handle should name one instance for its whole life. If a component remounts as a new instance, the old handle should fail with an actionable error that names how to get the new one, not silently resolve to the replacement (F3; inference for the remount case). Playwright's snapshot refs are the browser precedent: valid against the latest snapshot, re-obtained after the page changes (F20).
- **Collisions.** WebMCP rejects a duplicate name in one `ModelContext` (F6). Two mounted instances of the same component registering the same tool name will collide unless the name embeds an instance key, which is one more reason to put instance identity in arguments (inference).
- **Explain absence.** Whichever approach is used, a stable state tool that reports unavailable instances or capabilities with a reason addresses the semantic loss in F9.

## Confidence and limitations

- **High:** spec text (F1 to F6), API caching and tool-search rules (F10 to F13), and the VS Code and Gemini CLI refresh code at the cited commits.
- **Medium:** that small relevant sets improve selection. Consistent across first-party and one third-party source, but each measurement uses its own benchmark, and none is on page-object tools.
- **Low:** the Codex row; the Claude Desktop row; practitioner reports in WebMCP issues (F9, F17), which are small, self-reported, or anecdotal.
- **Inference, not verified:** the `2026-07-28` grey-zone reading for page-backed lists; the 400 on removing a discovered deferred tool; full cache invalidation per mount under upfront loading in practice.
- **Not covered:** client source beyond the files cited; how each client renders protocol errors to the model; Ayme's relay behaviour (out of scope for this ticket).
- **No source compares** dynamic per-instance tools against stable parameterized tools or against tool search on the same tasks.

## Unanswered questions and smallest experiments

In priority order: the first two can overturn the recommendation, the rest refine it.

1. **H1/H2 head-to-head (decides the design).** Same page, same tasks, three variants: per-instance tools, one parameterized tool with handles, parameterized tools behind tool search. Measure task success, wrong-tool and stale-call rates, and input tokens, on one Claude and one OpenAI model. Include a "many repeated instances" page and a "frequent remount" page.
2. **A. Removing a discovered deferred tool (Claude API and Claude Code).** Discover a deferred tool, drop its definition, send the next request. Record whether the API returns the 400 from F11 and what Claude Code does when an MCP server removes a tool the model already loaded.
3. **B. Cache cost of churn.** Over two requests, add and remove (a) an upfront tool and (b) a deferred definition; compare `cache_read_input_tokens`. Confirms F10 in practice and settles whether deferred-array changes touch the prefix.
4. **C. Propagation latency.** Time from `toolchange` (or server `list_changed`) to the first model request that reflects it, per client in the support table.
5. **D. Stale call surface.** Call a tool that was just removed and record the exact text the model receives in each client (protocol error shown, hidden, or replaced).
6. **E. Codex and Claude Desktop.** Run a server that toggles one tool on a timer and check whether each client's tool list follows it.
