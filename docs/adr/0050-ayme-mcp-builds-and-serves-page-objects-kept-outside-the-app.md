# `ayme mcp` builds and serves Page Objects kept outside the app, and the browser automation loads them through its init script

An agent that drives a browser through Playwright MCP or Playwright CLI gets Ayme's tools only on a page whose app ships Ayme with the Agent Connection on, and most pages it works on don't. So `ayme mcp` serves a project's Page Objects itself, experimental under ADR-0037, as a step towards Ayme's Node-side support rather than a replacement for it. The user writes one entry, `.ayme/page-objects.ts`, whose default export is the Page Object classes to register, the shape of `createAyme`'s `pageObjects` option; `ayme mcp` finds it in the folder it starts in, and a flag points at another. It builds the entry with esbuild through the build plugin's esbuild adapter, as ES modules, and every import resolves from the entry's folder as in a build of the project, so the page runs the project's own `@ayme-dev/ayme`, the one the Page Objects import. The build is served on the server's own loopback HTTP server, the extension ADR-0049 added for the external Inspector, which answers only loopback `Host` headers: no new server and no new port. On startup `ayme mcp` writes `.ayme/init-script.js`, which names its port, and adds it to `.ayme/.gitignore`. The browser automation runs that file as its init script: in each top-level document it imports the served runtime and entry, starts the runtime with the Agent Connection on and registers the entry's classes, and the agent pairs the tab with `ayme_connect` as on any app. An MCP server becomes a build server too, and the page fetches its code from `ayme mcp` on every load.

We rejected three alternatives. The user building one file with their own bundler and pointing the init script at it keeps old Page Objects in every tab until a new tab opens, and loads the Inspector and every lazy part eagerly. A fixed loader that scans the port range for a server, so that the init script never changes, cannot tell several `ayme mcp` servers on one machine apart, one per worktree. Serving a runtime bundled in `@ayme-dev/mcp` can drift from the version of `@ayme-dev/ayme` the Page Objects are written against.
