# Page Object Actions declare their own availability, and every unavailable tool says why

ADR-0020 made availability a runtime measurement of a Page Object's root and let it decide which tools are published, with no say for the application. That left an author whose action is possible only in some states, such as removing a dashboard that is not built in, with two bad options: root a Page Object at the one control so the tool comes and goes, or keep the action on its natural Page Object and let it throw. Either way nothing tells an agent why. The same silence hits the runtime's own cases: a tool withdrawn behind an open layer looks the same as one that never existed, and a tool left listed behind one fails with a locator timeout. We change three things. An action may carry an availability predicate, `available: async (self) => true | string`, a module-level function the build plugin lifts into the compiled registration beside the class; it runs read-only with the observation, never with the call, and the string it returns is the reason. Availability no longer adds or removes tools: every action of a present Page Object is listed, and calling an unavailable one refuses with its reason and no side effect; only presence still withdraws tools. Each unavailable tool carries exactly one Availability Reason of three kinds, `obstructed` with the Structural Ref of the element a click would hit instead, `ambiguous` when the root matches several elements, and `condition` with the author's string; the runtime reports only what it measured and never names a modal, popover or banner it cannot tell apart. The agent learns about changes where it already looks: the note on every tool result that lists tools that appeared or disappeared now also lists tools that became available or unavailable, with the reason, and `ayme_list_tools` carries `available` and `reason` on every tool; MCP's own tool list changes only on presence, since it has no field for availability and a reason in a description would go stale in agents that cache the list. We considered a separate decorator per condition, rejected because one `canX` often guards several actions and the predicate wires to each; a synchronous predicate, rejected because the observation runs in the page and locator reads are asynchronous; and runtime reasons that name the covering widget, rejected because hit-testing yields an element, not an intent. The cost is that the predicate's expression may only use module-scope names, never `this` or class privates, which the plugin rejects at build time; and that ADR-0020's rule against consumer configuration of availability now holds for Page Object availability only.

This decision amends ADR-0020.
