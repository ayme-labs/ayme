# A build includes Ayme only when its configuration says so

Turning WebMCP publication off leaves the runtime, its WebMCP driver and every Page Object Model body in the browser output (ADR-0030): 800 kB and more on a quickstart app, while most apps use Ayme only in development and WebMCP itself is still behind a browser flag. The build plugin therefore takes one explicit boolean, `include`, false by default, and nothing else decides. A build without Ayme resolves the runtime, its internal entry and each framework package to an absent entry, and compiles each Page Object Model to a stand-in that keeps the class and the module's other exports, so application code that imports Ayme still loads; a removed action or method rejects with an error naming what is missing, setup that enables publication logs an error once and leaves the app running, and every build prints one line saying whether Ayme is in it. The option is explicit rather than inferred from the bundler because Vite treats every `vite build` as production, staging included, and Next tells only the dev server from a build, so no inference could say what a team means, while a boolean that a config file computes can. We rejected deriving removal from the publication setting, which is a runtime value a build cannot see; tree-shaking behind a define, which cannot drop code the application imports by name; and removing the runtime while keeping model bodies, which would still ship every locator and label. Removal is all or nothing, which is what makes it checkable on built output. This settles the removal that ADR-0030 left open.
