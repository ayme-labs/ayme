# The `.ayme` folder

What your project keeps in `.ayme/`, how to set the folder up for your Page Objects, and which of its files you commit.

`.ayme/` sits at your project's root, beside `package.json`. Your Page Objects live there, and ayme's tools and skills read and write there:

```text
.ayme/
  tsconfig.json        the folder's compiler options
  pom/                 your Page Object Models, one class per file
  page-objects.ts      the classes `ayme mcp` serves to a page without ayme
  CONVENTIONS.md       what you settled for how ayme's skills work here
  product-surfaces/    the `product-surfaces` skill's list
  .gitignore           names the two generated entries below
  init-script.js       generated by `ayme mcp`
  recordings/          generated by the recorder
```

An app that ships ayme needs only `tsconfig.json` and `pom/`. Each other entry appears when you use the tool or skill it belongs to:

- `page-objects.ts` and `init-script.js`: [Page Objects on a page without ayme](page-objects-without-ayme.md), which is experimental.
- `CONVENTIONS.md` and `product-surfaces/`: [Coding agent skills](coding-agent-skill.md).
- `recordings/`: the recorder, `ayme-recorder codegen` in `@ayme-dev/cli`.

## Set the folder up for Page Objects

1. Put each [Page Object Model](ayme-page-objects.md) in its own file, `.ayme/pom/<ClassName>.ts`. Files inside `.ayme/` import each other by relative path.

2. Add `.ayme/tsconfig.json`. It gives the folder your app's compiler options, so the build plugin, `ayme mcp`, the type check and your editor all compile the Page Objects the same way:

   ```jsonc
   // .ayme/tsconfig.json
   {
     "extends": "../tsconfig.json",
     "include": ["**/*.ts"],
   }
   ```

   `extends` names the tsconfig that holds your app's compiler options. The table shows where each framework's template keeps them. If yours are in another file, such as `paths` you added to `tsconfig.app.json`, extend that file:

   | Project                        | `extends`                                                              |
   | ------------------------------ | ---------------------------------------------------------------------- |
   | Vite's React and Vue templates | `../tsconfig.app.json`                                                 |
   | SvelteKit                      | `../tsconfig.json`                                                     |
   | Angular                        | `../tsconfig.json`                                                     |
   | Next.js                        | `../tsconfig.json`, with `"compilerOptions": { "incremental": false }` |
   | Nuxt                           | `../.nuxt/tsconfig.app.json`                                           |

   The tsconfig it extends must turn `experimentalDecorators` on. No other tsconfig needs to include `.ayme/`.

3. Add the `#pom/*` alias to your `package.json`:

   ```json
   { "imports": { "#pom/*": "./.ayme/pom/*.ts" } }
   ```

   App code and tests import the Page Objects through it, the same way from any folder:

   ```ts
   // src/main.tsx
   import { ProjectsPage } from "#pom/ProjectsPage";
   ```

4. Add `tsc --noEmit -p .ayme` after your type check command. Your app's own type check sees only the Page Objects the app imports; this one checks the whole folder.

   ```json
   { "scripts": { "typecheck": "tsc -b && tsc --noEmit -p .ayme" } }
   ```

Four kinds of project need one thing more:

- **Angular.** `ng add` points the build plugin at `tsconfig.app.json`, so the build reads that file, not the folder's. Keep options your Page Objects need, such as `paths`, in the root `tsconfig.json`, which both extend.
- **Next.js.** Its tsconfig turns `incremental` on, and without `"incremental": false` the type check writes `.ayme/tsconfig.tsbuildinfo`. Point the Turbopack loader's `tsconfigPath` at `.ayme/tsconfig.json`.
- **Nuxt and SvelteKit.** They generate the tsconfig this chain ends in, in `.nuxt/` and, on SvelteKit 2, `.svelte-kit/`, when their dev server or build runs, and with `nuxt prepare` or `svelte-kit sync`. In a fresh clone, run one of those before `ayme mcp` or the type check: without the generated file, neither can read the folder's tsconfig.
- **A project with no tsconfig to extend**, such as one that only drives a site it doesn't build. Put the compiler options in `.ayme/tsconfig.json` itself:

  ```json
  {
    "compilerOptions": {
      "target": "ES2022",
      "module": "ESNext",
      "moduleResolution": "Bundler",
      "strict": true,
      "skipLibCheck": true,
      "experimentalDecorators": true,
      "noEmit": true
    },
    "include": ["**/*.ts"]
  }
  ```

## What you commit

Commit what you and your coding agent's skills write in `.ayme/`. Ignore what a tool generates there, with a `.ayme/.gitignore` you commit:

```text
init-script.js
recordings/
```

`ayme mcp` and the recorder each add their own line to that file. When the recorder writes the file first, it adds a `.gitignore` line too, which hides the file from git: remove that line to commit the file.

## Move Page Objects from another folder

1. Move the files to `.ayme/pom/` and add `.ayme/tsconfig.json`, as above.
2. Add the `#pom/*` alias, as above, and change every import of them in app code and tests to it. Imports between the files in `.ayme/` stay relative. Search for the old folder's name as well. Another alias, such as `$lib/pom/…` or `@pom/…`, and a path in a string, such as `new URL("../playwright/pom/…", import.meta.url)`, still point at it.
3. Remove the old folder from the `include` and the `paths` of your other tsconfigs.
4. Look at the build plugin's `tsconfigPath`, if it has one. In Angular, keep the one `ng add` wrote, which names your app's tsconfig. In Next.js, point the loader's at `.ayme/tsconfig.json`. Anywhere else, remove one that names a tsconfig made for the old folder: without the option, the plugin reads `.ayme/tsconfig.json`.
