# Ayme source layout

`src/` is cut into slices named for what they do, with layers inside a slice only where it has them so far. [`eslint.config.js`](eslint.config.js) is the source of truth for which slices and layers each may use; `pnpm lint` flags a misplaced import, and `src/layout.test.ts` checks that it does. Every kind of import counts: static, dynamic, type-only and a type written as `import("…")`. A dynamic `import()` names its module with a string literal, so lint can read it.

Slices, from the bottom up:

- `shared`: the JSON contracts and tool descriptors, the error types, the Caller names, schema validation, the Goal Loop's contract with its Caller (the `goal` tool's input and the Handover), and small helpers: the composed tree, the monotonic clock, the Inspector's page marks.
- `in-page`: the In-page Module ([ADR-0049](../../docs/adr/0049-one-in-page-module-per-document.md)): one per document, installed by the first Host and bound by every later one. It captures, keeps the document's refs, watches the document's activity and navigations, and runs an action's Settled Page wait with core's, telling each Host of its Visits and of a full load that ends its action. Its `page` part runs in the document and is the only code allowed the browser's globals; the build turns it into self-contained functions ([`build/inPageModule.ts`](build/inPageModule.ts)), with Playwright's snapshot code taken from the pinned InjectedScript and given marks and a ref counter of the document's own ([`build/pinnedAriaSnapshot.ts`](build/pinnedAriaSnapshot.ts)). Its `host` part is DOM-free and reaches the module only through Playwright's `Page`, but for the files [`eslint.config.js`](eslint.config.js) still allows the browser's globals, each with the issue that removes it. Highlights are Playwright's `locator.highlight` on `ayme-ref=` locators, which set nothing on the app's elements; the page's activity watchers ignore the overlay host Playwright adds under `<html>` (`onlyOwnMarks` in `shared`). Picking a Structural Ref and Demo Mode's click cue run in the page part and are reached through `inPage(page).pick` and `.cue`. It uses only `shared` and `@ayme-dev/core`, and only a slice's `infrastructure` and `runtime` use it.
- `page-state`: the Structural Page State and its Page State Session, the interaction history it records, Change Records and the per-Caller cursors, Structural Refs and Ayme's selector engine, acting on the page through the in-page module, Page Object Root Marks and root placement in the captured tree, and reach: whether a click would land on an element, and the refusal when a call would not run.
- `runs`: the Run, the Run queue and executing a top-level Run, the Run log, Interactions and the Playwright call table, and the page instrumentation that records a Run's Interactions and gives the runtime's Pages Demo Mode (pace, click cue) and the pointer actions' pass-through of the Inspector's host.
- `page-objects`: the `@ayme` marks, the Page Object registry and the page driver it reads the page through, the Page Object tree, instances, roots, presence and availability, action tool facts, Page Object definitions and their text, and `createPage`.
- `tools`: the Browser Tools, Custom Tools, Peek Tools, page context, screenshots and the agent's image calls the Inspector shows, and the built-in tools' input and result types.
- `goal-loop`: the Goal Loop, the Step Decision and its questions, the operations it offers, the decision wire, and the Decision Endpoint's client and handler.
- `runtime`: the composition root: `createAyme`, the runtime options, the published tools, WebMCP publication, the Inspector and the Agent Connection.

The entries (`index.ts`, `internal.ts`, `inspector.ts`, `absent.ts`, `server.ts`, `testing.ts`) stay at the top of `src/` and use the slices' front doors. No slice uses an entry. `server.ts`, the `./server` entry, only re-exports the Decision Endpoint's handler from `goal-loop`. `inspector.ts`, the `./inspector` entry, is the Inspector contract (plain data in `shared`) and the runtime's inline serving of it.

Layers: `domain` (pure rules and types), `application` (the flows and the ports they use), `infrastructure` (the network, the DOM and Playwright Lite's page). `page-state`, `page-objects`, `goal-loop`, `runs` and `tools` are layered. `shared`, `in-page` and `runtime` stay unlayered.

- Every file of a layered slice sits in a layer folder. A layered slice has no `index.ts` of its own: each of its layers that other code uses has a front door, the `index.ts` in that layer's folder.
- The layer order that [`horizontal-boundaries.js`](../eslint-config/horizontal-boundaries.js) sets inside a slice holds across slices too, so lint judges an import through another slice's front door by the layer the door sits in. The imports that still break it are listed in [`eslint.config.js`](eslint.config.js), each with the issue that removes it; [ADR-0046](../../docs/adr/0046-the-layer-order-holds-across-slices-through-one-front-door-per-layer.md) says why.
- No production file imports Playwright Lite's internal entry. The files that still do are allowlisted in [`eslint.config.js`](eslint.config.js), each with the issue that removes it, and `src/layout.test.ts` fails when one no longer needs to.
- `domain` and `application` reach the browser only through what they are handed: a Run carries its Page, its Document, its Page State Session and its Reach, and a port's adapter in `infrastructure` does the rest. Outside tests, lint refuses them Playwright Lite and the browser globals that [`eslint.config.js`](eslint.config.js) lists; it also names the one module still allowed Playwright Lite. A store that every copy of the bundle shares sits on `globalThis` in its slice's `infrastructure`.
- A `domain` rule may read an `Element` it is handed, as the Goal Loop's questions and the Browser Tools' element filters do; capturing the page or acting on it is not a rule.
- In `page-state`, the Page State Session reads the page only through its ports: the capture, which answers the in-page module's plain-data capture, the action page, which begins an action in the module and answers how it ended (settled, threw or a full load), and, until #1182, the browser's lookup of the elements a capture's refs name. `infrastructure/browserInPage.ts` is the browser runtime's host of its document's module, through its own Playwright Lite page, and the session records the Visits the module reports; jsdom tests stand in for it with `src/test-utils/inPageCapture.testSupport.ts`. The per-document stores (the sessions, the cursors, the Page Object structure source, the ignore predicate) and the functions code outside a Run reaches a document's session through live in `infrastructure/pageState.ts`; a tool reaches it through its Run. Reach is a port too, in `application/reach.ts`: `infrastructure/reachMeasurement.ts` is its Chromium geometry adapter, the runtime picks the adapter a session measures with, and a unit test hands its own in (`src/test-utils/reach.testSupport.ts`). `domain` and `application` hold no module state.
- In `page-objects`, the registry and the walk of the Page Object tree read the page through the page-driver port in `application/pageDriver.ts`. `infrastructure/inPageDriver.ts` is its one adapter, over the in-page module, for Playwright Lite and Playwright alike: a Page Object Root is probed in the page, where its presence and reach are measured with its Locator resolved, and the registry holds refs, never elements. `infrastructure/registry.ts` holds the one browser registry, built on it. A call of a Page Object Tool checks its root through the driver too.
- In `goal-loop`, `infrastructure/goalLoopStore.ts` keeps the configured decision function and the last run's result, and builds the `goal` tool from them.
- In `tools`, a tool runs in `application` against the browser Page its Run carries, a Playwright `Page`, and keeps its name, description, input schema and the reach it needs beside its execution. The element predicates (clickable, fillable, checkable, uncheckable, select) run in the In-page Module: a capture carries the refs each asked predicate keeps, and the Goal Loop's options come from those sets; a Custom Tool's own `Element` filter is the one exception until #1177. `infrastructure` holds `generate_locator`, whose Locator Recommendation the In-page Module generates with Playwright's own generator, the list of published Browser Tools, which includes it, and the stores the bundle copies share, with what they build: the Custom Tools and the element tools they join, the router function and the navigation tools, and the Peek registry. The runtime tells a Peek which side it is on.
- Another slice is reached through its front doors. A front door re-exports only what other slices, the entries and tests use, and only from its own layer's modules, or its own slice's when the slice is unlayered. Inside a slice, a module imports the module it needs, never its own slice's front doors.
- A module sets up on import only the state its own exports use, so the build drops the modules an entry does not use: `src/builtEntries.test.ts` checks that the built `./server` and `./absent` entries carry no browser runtime.

The In-page Module's contract suite (`in-page/host/inPageContract.testSupport.ts`) runs in both lanes: in the browser lane over Playwright Lite, and in the unit lane over real Playwright Chromium against the built package, which is what catches an install function that closes over host state.

Tests stay beside the module they are about, in its layer folder when the slice is layered, even when they start a whole runtime: the slice order holds for production code only. They still reach another slice through its front doors, except `vi.mock` and `vi.importActual`, which name the module file itself, since mocking a front door leaves the slice's own imports of that module alone. A mock factory that keeps the rest of such a module spreads `await importOriginal<object>()`. Harnesses that several slices' tests share live in `src/test-utils/`; one slice's own harness lives in that slice, in its `test-utils/` layer when it is layered. Production code never imports test code.
