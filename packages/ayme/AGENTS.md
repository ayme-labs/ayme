# Ayme source layout

`src/` is cut into slices named for what they do, with layers inside a slice only where it has them so far. [`eslint.config.js`](eslint.config.js) is the source of truth for which slices and layers each may use; `pnpm lint` flags a misplaced import, and `src/layout.test.ts` checks that it does. Every kind of import counts: static, dynamic, type-only and a type written as `import("…")`. A dynamic `import()` names its module with a string literal, so lint can read it.

Slices, from the bottom up:

- `shared`: the JSON contracts and tool descriptors, the error types, the Caller names, schema validation, the Goal Loop's contract with its Caller (the `goal` tool's input and the Handover), and small helpers: the composed tree, the monotonic clock, the Inspector's page marks.
- `in-page`: the In-page Module ([ADR-0049](../../docs/adr/0049-one-in-page-module-per-document.md)): one per document, installed by the first Host and bound by every later one. It captures, keeps the document's refs, watches the document's activity and navigations, and runs an action's Settled Page wait with core's, telling each Host of its Visits and of a full load that ends its action. Its `page` part runs in the document and is the only code allowed the browser's globals; the build turns it into self-contained functions ([`build/inPageModule.ts`](build/inPageModule.ts)), with Playwright's snapshot code taken from the pinned InjectedScript and given marks and a ref counter of the document's own ([`build/pinnedAriaSnapshot.ts`](build/pinnedAriaSnapshot.ts)). Its `host` part is DOM-free and reaches the module only through Playwright's `Page`, but for the files [`eslint.config.js`](eslint.config.js) still allows the browser's globals, each with the issue that removes it. Highlights are Playwright's `locator.highlight` on `ayme-ref=` locators, which set nothing on the app's elements; the page's activity watchers ignore the overlay host Playwright adds under `<html>` (`onlyOwnMarks` in `shared`). Picking a Structural Ref and Demo Mode's click cue run in the page part and are reached through `inPage(page).pick` and `.cue`. It uses only `shared` and `@ayme-dev/core`, and only a slice's `infrastructure` and `runtime` use it.
- `page-state`: the Structural Page State and its Page State Session, the interaction history it records, Change Records and the per-Caller cursors, Structural Refs and Ayme's selector engine, acting on the page through the in-page module, Page Object Root Marks and root placement in the captured tree, and reach: whether a click would land on an element, and the refusal when a call would not run.
- `runs`: the Run, the Run queue and executing a top-level Run, the Run log, Interactions and the Playwright call table, and the page instrumentation that records a Run's Interactions and gives the runtime's Pages Demo Mode (pace, click cue) and the pointer actions' pass-through of excluded subtrees (the generic `data-ayme-exclude` mark, which the inline Inspector sets on its host unless it is mounted for dogfooding).
- `page-objects`: the `@ayme` marks, the Page Object registry and the page driver it reads the page through, the Page Object tree, instances, roots, presence and availability, action tool facts, Page Object definitions and their text, and `createPage`.
- `tools`: the Browser Tools, Custom Tools, Peek Tools, page context, screenshots and the agent's image calls the Inspector shows, and the built-in tools' input and result types.
- `goal-loop`: the Goal Loop, the Step Decision and its questions, the operations it offers, the decision wire, and the Decision Endpoint's client and handler.
- `runtime`: the composition root: `createAyme`, the runtime options, the published tools, WebMCP publication, the Inspector and the Agent Connection. With the `inspector` option's external placement it mounts no panel and hands the page client the Inspector contract as plain data (`inspectorChannelPort`, loaded on demand), which `@ayme-dev/mcp` relays to a window it serves.
- `compiler`: the Page Object compiler, for Node: it derives each Page Object Model's manifests and tool schemas from its TypeScript types, rewrites its `@playwright/test` imports to Playwright Lite, compiles it to the module a build registers, or to its stand-in in a build without Ayme, and transpiles its decorators. It keeps one TypeScript Program per tsconfig project until the bundler adapter that owns it says its inputs may have changed ([ADR-0036](../../docs/adr/0036-bundler-adapters-own-the-lifetime-of-compiler-state.md)). It is the only code that imports `typescript`, an optional peer, and it uses only `shared` and `page-objects`' domain. Only the `compiler` entry uses it. Its fixtures under `fixtures/` folders are Page Object Models as a project writes them, importing Ayme by its package name, so lint and the package's typecheck skip them.

The entries (`index.ts`, `internal.ts`, `inspector.ts`, `absent.ts`, `server.ts`, `playwright.ts`, `testing.ts`, `compiler.ts`) stay at the top of `src/` and use the slices' front doors. No slice uses an entry. `server.ts`, the `./server` entry, only re-exports the Decision Endpoint's handler from `goal-loop`. `playwright.ts`, the `./playwright` entry, is Ayme over a Playwright Page a Node host hands it (ADR-0049): `createAyme({ page, ... })` runs `runtime/session.ts`, the session code the browser runtime shares, over that Page; the built entry carries no browser runtime, which `builtEntries.test.ts` checks, so nothing it reaches may import Playwright Lite or the `document`. The browser's own facades (`pageOfDocument(document)` and the functions built on it) sit in files of their own beside the Page-keyed ones for that reason. `inspector.ts`, the `./inspector` entry, is the Inspector contract (plain data in `shared`) and the inline Inspector's way to the runtime's contract, a slot on the document the browser session publishes to; it carries no runtime code, which `builtEntries.test.ts` checks. The Agent Connection serves the same contract to an Inspector in another window (`runtime/externalInspector.ts`).

Layers: `domain` (pure rules and types), `application` (the flows and the ports they use), `infrastructure` (the network, the DOM and Playwright Lite's page). `page-state`, `page-objects`, `goal-loop`, `runs` and `tools` are layered. `shared`, `in-page`, `runtime` and `compiler` stay unlayered.

- Every file of a layered slice sits in a layer folder. A layered slice has no `index.ts` of its own: each of its layers that other code uses has a front door, the `index.ts` in that layer's folder.
- The layer order that [`horizontal-boundaries.js`](../eslint-config/horizontal-boundaries.js) sets inside a slice holds across slices too, so lint judges an import through another slice's front door by the layer the door sits in. The imports that still break it are listed in [`eslint.config.js`](eslint.config.js), each with the issue that removes it; [ADR-0046](../../docs/adr/0046-the-layer-order-holds-across-slices-through-one-front-door-per-layer.md) says why.
- No production file imports Playwright Lite's internal entry. The files that still do are allowlisted in [`eslint.config.js`](eslint.config.js), each with the issue that removes it, and `src/layout.test.ts` fails when one no longer needs to.
- `domain` and `application` reach the browser only through what they are handed: a Run carries its Page, its Navigation, its Page State Session and its Reach, and a port's adapter in `infrastructure` does the rest. Outside tests, lint refuses them Playwright Lite and the browser globals that [`eslint.config.js`](eslint.config.js) lists; it also names the one module still allowed Playwright Lite. Every store is keyed by `Page` (the browser runtime's by its own Playwright Lite page, a Node host's by the Page it was handed), and none sits on `globalThis`; the two exceptions are the process's Peeks (a Node process has no Page) and the Goal Loop's test readout.
- A `domain` rule reads refs and the Structural Page State, never an `Element`; capturing the page or acting on it is not a rule.
- In `page-state`, the Page State Session reads the page only through its ports: the capture, which answers the in-page module's plain-data capture, the action page, which begins an action in the module and answers how it ended (settled, threw or a full load). Nothing in it names an element: it holds refs and asks the module for the rest. `infrastructure/browserInPage.ts` is the browser runtime's host of its document's module, through its own Playwright Lite page, and the session records the Visits the module reports; jsdom tests stand in for it with `src/in-page/inPageStandIn.testSupport.ts`. The per-Page stores (the sessions, the cursors, the Page Object structure source, the `ignore` and Custom Tool filters, whose Locators each capture hands the module the matches of first) live in `infrastructure/pageStates.ts`, and a session starts a fresh history and identity ledger when a capture is of another document than its last, as a Node host's Page outlives its documents; the functions code outside a Run reaches a browser document's session through live in `infrastructure/pageState.ts`; a tool reaches it through its Run. Reach is a port too, in `application/reach.ts`: `infrastructure/reachMeasurement.ts` is its Chromium geometry adapter, the runtime picks the adapter a session measures with, and a unit test hands its own in (`src/test-utils/reach.testSupport.ts`). `domain` and `application` hold no module state.
- In `page-objects`, the registry and the walk of the Page Object tree read the page through the page-driver port in `application/pageDriver.ts`. `infrastructure/inPageDriver.ts` is its one adapter, over the in-page module, for Playwright Lite and Playwright alike: a Page Object Root is probed in the page, where its presence and reach are measured with its Locator resolved, and the registry holds refs, never elements. `infrastructure/registry.ts` holds the one browser registry, built on it. A call of a Page Object Tool checks its root through the driver too.
- In `goal-loop`, `infrastructure/goalLoopStore.ts` keeps the configured decision function and the last run's result, and builds the `goal` tool from them.
- In `tools`, a tool runs in `application` against the browser Page its Run carries, a Playwright `Page`, and keeps its name, description, input schema and the reach it needs beside its execution. The element predicates (clickable, fillable, checkable, uncheckable, select) run in the In-page Module: a capture carries the refs each asked predicate keeps, and the Goal Loop's options come from those sets; a Custom Tool's own filter, a selector or a function the session calls once with its Page for a Locator, keeps its refs in the module too: a selector is matched in the capture (checked when the session starts, through the slot's `check` in Node), and a Locator's matches are handed to the module before each capture (`inPage(page).match`). Its `execute` gets a ref and a Locator, never an element. `infrastructure` holds `generate_locator`, whose Locator Recommendation the In-page Module generates with Playwright's own generator, the list of published Browser Tools, which includes it, and the stores the bundle copies share, with what they build: the Custom Tools and the element tools they join, the router function and the navigation tools, and the Peek registry. The runtime tells a Peek which side it is on.
- Another slice is reached through its front doors. A front door re-exports only what other slices, the entries and tests use, and only from its own layer's modules, or its own slice's when the slice is unlayered. Inside a slice, a module imports the module it needs, never its own slice's front doors.
- A module sets up on import only the state its own exports use, so the build drops the modules an entry does not use: `src/builtEntries.test.ts` checks that the built `./server` and `./absent` entries carry no browser runtime, and that only the built `./compiler` entry imports TypeScript.

The In-page Module's contract suite (`in-page/host/inPageContract.testSupport.ts`) runs in both lanes: in the browser lane over Playwright Lite, and in the unit lane over real Playwright Chromium against the built package, which is what catches an install function that closes over host state.

Tests stay beside the module they are about, in its layer folder when the slice is layered, even when they start a whole runtime: the slice order holds for production code only. They still reach another slice through its front doors, except `vi.mock` and `vi.importActual`, which name the module file itself, since mocking a front door leaves the slice's own imports of that module alone. A mock factory that keeps the rest of such a module spreads `await importOriginal<object>()`. Harnesses that several slices' tests share live in `src/test-utils/`; one slice's own harness lives in that slice, in its `test-utils/` layer when it is layered. Production code never imports test code.
