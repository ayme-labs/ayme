# Recorder engine source layout

The engine of the Recorder: it starts a recorder on the Playwright the project has installed, records every kind of input as Interactions, and ends with a Recording Package or with "empty". It is internal; the CLI (`packages/cli`) starts it, and the window (`packages/recorder-window`) knows only its `./contract` entry. Why it runs on stock Playwright: [ADR-0052](../../docs/adr/0052-the-recorder-runs-on-stock-playwright-and-uses-its-private-parts-only-under-test.md).

`src/` is cut into slices named for what they do, with layers inside a slice only where it needs them. [`eslint.config.js`](eslint.config.js) is the source of truth for which slices and layers each may use, and for where Playwright and Effect may be imported; `pnpm lint` flags a misplaced import, and `src/layout.test.ts` checks that it does.

Slices, from the bottom up:

- `contract`: the plain data shared with the CLI, the window and the toolbar: the outcome, the state with its phase (and, while it wraps up, what that leads to), the commands that apply now, the address of the page that is open and the Visits and entries recorded so far, updates with their counter, commands and their answer, and the messages the in-page toolbar sends through the one page function the engine gives it. Types only. It is the `./contract` entry. Every entry has an `id`, the one a decision names; an entry the person left out is marked `discarded`. What an entry changed crosses as change rows, plain data made for whoever shows a recorder, never as a tree or as the package's text.
- `timeline`: Visits, snapshots and Interactions in, the Visits with their entries out as they are produced, and the Recording Package at the end. `domain` holds what a recording is made of in the engine's words (`recorded.ts`), the `Timeline`, which keeps Visits and element identity with core's observation session and compares snapshots with core's trees, the rule that finds an Interaction's target (`target.ts`), the released package text (`packageText.ts`), an entry's change rows (`changeRows.ts`) and how an element is named for whoever shows it (`elementNames.ts`: by a label that fits it alone on its page, built as Playwright builds a locator: its role and name, then with the text inside it, then inside its nearest ancestor whose label fits that ancestor alone, and its place last. Each label has a Playwright selector of the same words, and fits its element alone as that selector matches by Playwright's rules: a name exactly, a role alone every element of the role, an element's own text exactly, the text inside as part of a text in any case, a text with no role as the innermost element whose text it is; each in the element's own document, a frame's being its own; its place counts those matches. A snapshot writes a name the same whether it is the element's text or an aria-label, which is no text: a text that one element's name alone may or may not hold names nothing, and an element with a role whose own text it is is named by its role and its place instead (`unsureOf`). What each selector matches is worked out once per naming of a read or a Change Tree and page, with exact names and texts indexed (`PageLabels`), and kept only while that naming lasts (`ElementNames`): the timeline names a Change Tree's rows once, as it makes the tree, and keeps the labels, plain data, and no index, as it keeps every read and Change Tree to the save. A text held inside is looked for only in the elements that have the rarest of its three-letter pieces (`TextsHolding`), so labelling a list of items with texts of their own takes a time that grows about as the list does: only texts that all share every piece take the square of their number. A removed element is counted against the page before the change, which that naming builds only when it names a removed element (`foundRows`), not the reconciled tree's order; the rule for an element with no role and no name is written there and in `changeRows.test.ts`). The timeline keeps what each entry changed as core's Change Tree, with how each node stood before, until the save: the package text and the rows are two renderings of that one tree, the text at the save and the rows when the entry is made, so the package is written from the very entries a subscriber was told. Renaming a tree's refs to the first refs carries how each node stood before along (`underFirstRefs`). The press of a held click reaches the page before the gate holds the click, so the read before it already shows the focus the press moved: when the element that gained it is the clicked one or one around it, that read stands with the focus where the read before had it for the step before the click and for the click's own change (`beforeItsPress`), so the move is the click's. When the click starts where the Interaction before it ends, as right after typing, that Interaction is measured again to the read as it stood (`pressedAfter`): it keeps what it did itself, and the move is the click's. An Interaction added under a key may still change, as typing does while it is typed: added again under that key, its entry is replaced in place, with its id, its place and the change of its own ahead of it, measured again from its first picture up to its new "after" (`replace`); a `text` addition replaces only its text. An input known from its report that is written before the page is read again matches Playwright's picture with its "before" alone (`pictureBefore` without `between`): an element the picture has and the "before" has not gets a ref of its own until a later read lists it, and is then named by that read's ref (`tie`), so the row that showed and the package name the same element. `infrastructure` writes the package where the released recorder keeps its recordings, with the recording's trace file beside it, under a temporary name that it renames, makes the first save write `.ayme/.gitignore` (the recordings folder and itself; never over a project's own file; no browser profile, which the rebuild keeps none of), and finds a recording's trace for `trace`. No Effect: its work is promises.
- `session`: one live recorder. `domain` holds the lifecycle, one pure function (`step`) from a state and one thing that happened to a new state and a list of things to do, and the start error. `application` holds the queue with its one worker (`RecorderSession`), which feeds `step` and carries out its list in order, and the engine's one seam, the recorded browser (`RecordedBrowser`), which speaks the engine's words and never Playwright's.
- `playwright`: the stock Playwright adapter of the recorded browser. It finds the project's own Playwright, launches Chromium with it or attaches to a running one, and carries out the engine's requests on it. Launching and attaching differ only in how the adapter gets its browser and lets go of it: an attached browser's open page gets the page scripts at once, and is put back as it was found before the connection closes, never closed. Its `infrastructure` is in three parts, by how each is measured ([docs/testing.md](../../docs/testing.md#code-a-real-browser-runs)): `live/` drives the browser (`stockBrowser.ts`, the adapter, and `pageFunctions.ts`, which sends each page function with its rules), `in-page/` is what runs inside a recorded page, and the plain logic beside them, such as `pageRules.ts`, the rules the page code decides by. What runs inside a recorded page is the gate that holds a click, a right-click or a middle click (by the event Playwright records it by, the context menu event or the auxclick, and sent on with its button), or a key press back, and every key after it until the page is let through (switched off, it goes on holding clicks and keys while an input it held still waits to be passed on); the watch that tells of the page's activity, a key typed into a field included, so that the quiet a Settled Page needs starts again at each key while its deadline runs from the start of the wait; and the target watch that tells which element an input acted on, as Playwright's selector names it, and the refs Playwright's picture gives it and its ancestors: the element under the pointer can be inside a link or a button, and Playwright's report gives that inner element's ref while its selector names the link or the button (`actedOnIndex` in `pageRules.ts` follows Playwright's rule for which; `reportTarget` in `reportTarget.ts` takes only the input's own note, the one whose element under the pointer Playwright's ref names, and otherwise reads a click's element through the selector, itself included, never from another input's note; the report gives the element's ref when its picture lists it, and the listed refs of its ancestors when not, `namedIn`; switching Playwright's recorder off is answered once every report still being read is told); the removal of the cursor mark Playwright's picking leaves on the body, which would wipe the clickable marks from every later snapshot; and the recorder's own highlight, drawn through a DevTools session of the page, never through Playwright. What a Settled Page is, core decides ([ADR-0024](../../docs/adr/0024-core-owns-the-meaning-of-a-settled-page.md)): the adapter gives core's `waitForSettled` the page's activity and nothing more, so no quiet window, deadline or retry lives in the adapter or in a page. When it is handed the toolbar's script (the engine never imports the window package: the CLI says where the script is), every document gets it after the gate and before the page's own scripts, beside the page function that answers through the bridge; an attached browser's open pages get it at once, and lose it when the adapter lets go. The gate leaves an input on the toolbar's host alone, and the toolbar stops it at the window before the page or Playwright's recorder hears of it. `projectPlaywright.ts` finds the project's Playwright and holds it to the supported range; `playwrightRecorder.ts` is the one place that knows how each supported version starts Playwright's own recorder and shapes its reports. `traceTool.ts` runs the project's own `playwright trace`: after a trace is stopped it asks the tool for the position numbers of the snapshot marks the adapter left in it, and `trace` passes through to it. The only slice that may import Playwright, types included.
- `server`: the window's server, on plain Node `http` and `ws` with tRPC, at a free port of the loopback address. `infrastructure/windowServer.ts` serves the window's built files from the folder it is handed (the engine never imports the window: the CLI says where it is) and the channel at `/channel`. It refuses a request whose `Host` is not `127.0.0.1` or `localhost`, or whose `Origin` is another page's, and answers a request it cannot parse as a bad request (400). `windowChannelRouter.ts` is the channel: the mutation `send` and the subscription `updates`, whose first message is the full state. It reaches the recorder only through the handle every caller gets, attached by the composition root, so there is no Effect in it. It closes when the recorder ends, after each window has been sent how it ended. `infrastructure/toolbarBridge.ts` is the in-page toolbar's way to the recorder: it answers the toolbar's messages through the same handle, a command as the recorder answers it and a request for the first update above the toolbar's revision at once or when it comes, so state is pulled and nothing calls into the page to tell a change. When the stock adapter launched the browser, it opens the window's address there in a context of its own, outside everything it records; when attached, the address is only printed.
- `engine`: the composition root and the front door. `startRecorder` picks the stock adapter, and for a launch asked to start recording (`startRecording`, the CLI's `--start-recording`) sends Record before it hands the recorder out: the adapter opens the page blank and sends it to its URL only once the pages hold inputs back, Record's last step, so that the first page load is in the recording and its trace (a page blank at Record gets its first Visit at its first address, `blankAtRecord`). A read of the document a page left is no start for what is done in the one it goes to: while recording or wrapping up after Stop, the page forgets its latest read at every navigation to another document, whatever took it there (a held click, the browser's Back button, a redirect, the blank page going to its address) (`leftDocument`), and a read of a document it has left that comes after, as one of the blank page or of the address it went on from, is not taken as its read (`keepRead`), so the first key typed there waits for a read of the new document and is in its Visit. A read carries the address the page was at as the read started (`takeSnapshot` in `stockBrowser.ts`), so a read a navigation overtook is not taken for the new document's, and the timeline stores no read of a document the page has left in the Visit of where it went (`sameDocument`: a change of the address's query or hash alone keeps the document, as it keeps the Visit): it stores it in the Visit of the document it is of, the latest of its page at its address, so an input whose read the navigation overtook, as an element picked or typing just before the page went, is kept there with that read; `startRecorderOn` turns a session on any recorded browser into the handle a caller gets, and is the one place Effect becomes promises. `runTrace` is the `trace` command: it says which trace file the arguments name (`latest`, a recording id or a path) and hands them to the project's own `playwright trace`. `runInstall` is the `install` command: it hands its arguments to the project's own `playwright install`.
- `testing/`, beside `src/`: the package's test support (ADR-0057), which other workspaces import from source as `@ayme-dev/recorder/testing`: `startScriptedRecorder`, a real recorder on a scripted browser that a test plays by hand.

Layers: `domain` (pure rules and types), `application` (the flows and the ports they use), `infrastructure` (Playwright, the disk, the network). `contract`, `engine` and `testing` aren't layered.

The layer order holds across slices as it holds inside one ([ADR-0046](../../docs/adr/0046-the-layer-order-holds-across-slices-through-one-front-door-per-layer.md)): domain uses domain, application uses application and domain, and infrastructure uses any layer.

- Every file of a layered slice sits in a layer folder. A layered slice has no `index.ts` of its own.
- Each layer that other code uses has a front door, the `index.ts` inside that layer's folder. Another slice imports the door of the layer it uses, such as `../../timeline/domain`, so lint judges the import by that layer. Inside a slice, import the module itself.
- An unlayered slice is reached through its own `index.ts`.
- An application module never imports another slice's infrastructure. What it needs done on the disk or in the browser it is handed: the composition root (`engine/recorder.ts`) gives the session the function that saves a package, and the recorded browser as a layer.
- `src/index.ts` is the package's front door. Nothing but promises, callbacks and plain data leaves it: `src/publicTypes.test.ts` fails when an Effect type or a Playwright type is reachable from the built entry.
- Ids and refs that could be taken for one another have a type of their own, each under a name no other type in the repository has: an entry's id (`EntryId`, in the contract), a page's (core's `PageId`), an input's (`InputId`, `session/domain/lifecycle.ts`), a snapshot's (`SnapshotId`) and where the trace holds it (`TracePosition`, both in `timeline/domain/recorded.ts`), and the three kinds of ref the timeline meets (`timeline/domain/refs.ts`). A value gets its type only where it is made or where it arrives, never by a cast on its way: the lifecycle makes snapshot ids and the ids of inputs known from a report; the stock adapter and the scripted browser make page and input ids and read Playwright's refs; `traceTool.ts` makes positions; the timeline makes entry ids and reads refs off core's trees; the window channel's command schema takes an entry id as it arrives from the window or the toolbar. Tests write them with the builders in `testing/ids.ts`, which serves every slice's tests since lint keeps a slice's tests out of another slice's folders; the scripted browser and the compatibility suite's harness take them as plain strings (`Written`, `session/domain/written.ts`).

The lifecycle decides and the adapter only carries out. To add behaviour, add a state, a thing that happened or a thing to do to `session/domain/lifecycle.ts`, with a row in its table test. The worker needs a change only for a new kind of thing to do. Which commands apply in a state (`offered`) is read from the lifecycle's own answer to each, so a new command needs no second rule for the window.

The engine asks the browser and the browser tells the engine, and both are plain data in `lifecycle.ts`:

- A new thing the browser can do is a member of `BrowserRequest`. The stock adapter and the scripted browser each carry it out in their one `switch`, and do nothing else there: no request leads to another, and no order is decided.
- A new thing the browser can tell is a member of `BrowserSignal`. What comes of a request is told that way too, never returned: the browser's signals are one stream, so the lifecycle sees an answer in order with what the browser noticed by itself.
- `ask` returns at once, for every request and in both adapters, and the answer comes later as a signal. The one worker never waits on the browser, so a page that is slow or stuck cannot keep a command or a time limit from being handled.
- A request the browser could not carry out, because it broke on the way, is answered by the "could not" signal, "requestFailed", which carries the request. The lifecycle says what follows for each kind of request (`failed` in `lifecycle.ts`), so that no state waits for an answer that cannot come: a new `BrowserRequest` gets its case there, with a row. Only a request for a page that is gone may be answered by nothing, since the page's closing was told.
- Playwright's reports come in the order of the inputs: a report is the oldest held input's of its page and its kind that has none, and a click's only of a click of the same button, so a click no page held, as a middle click on an element the gate leaves alone, never takes the report of another (`reportOfHeld`). A check's and an uncheck's report names no button: it is a left click's or a middle click's, never a right click's, as Playwright reports a middle click on a checkbox or a radio that way; a middle click is saved with it as the middle click it was (`asHeld`).
- Only an input a page holds back is ever passed on (`heldByItsPage`). An assertion and an input known from its report were never held: when the snapshot one of them waits for cannot be taken, nothing is passed on and nothing behind it waits (`withoutItsSnapshot`). An assertion is then written at its page's latest snapshot; a reported input starts there, or, on a page that has none, takes one snapshot of the Settled Page as its "before" and its "after", with a warning. What cannot be placed at all is left out with the warning "notRecorded".
- One trace per recording, decided by the lifecycle: `startTrace` at the first Record (Continue goes on in the trace that is running), `stopTrace` with `keep` at the save, which waits for "traceStopped" before the package is written, and without `keep` on Clear, which is not over, and takes no Record, until "traceDiscarded". Every trace request is answered by a signal, and the lifecycle asks for the next when the last is answered: Playwright is asked to report only once "traceStarted" is told, since a snapshot is marked in the trace, and a Record after a Clear starts its trace only when the old one is gone. The adapter queues none of them; what it serializes, the marks and the read of an upload's files, is one context-wide resource of Playwright's, not an order of requests. The adapter uses Playwright's public tracing and leaves a mark in the trace for each snapshot; the package's position numbers are the stock trace tool's numbers for those marks, taken from the tool itself, never counted from the archive. A trace that cannot be stopped does not lose the recording: the package is written without it.
- Playwright's own recorder is switched on and off with `reportInteractions`, by its mode: the stock adapter starts it once and never stops it. It is on while the recorder records and through a wrap-up, whose reports are still owed, and off whenever the recorder lives on without recording.
- Requests are carried out side by side. When one must follow another, the lifecycle asks for the second when the first is answered, as Record does: Playwright reports Interactions, then the pages hold inputs back, then Record is answered.
- A command is answered in the step that handles it, or, when its answer depends on the browser, kept with `deferReply` and given with `replyDeferred`. Every path out of that state gives the answer.
- Stop, Clear, Finish and an end from outside all end a stretch of recording through one wrap-up, which carries what it leads to (`then`). A new way to end a stretch is a new value there, not a second wrap-up. Through a wrap-up the pages hold inputs back as while recording until no input is under way, and only then are asked to hold no more (`gateOffAsked`): a click given after Stop, before "Paused" shows, gets a "before" of its own, which ends the Interaction still settling, and the wrap-up waits for its "after". A typed key a page held stays under way once it has reached its page, until the page is settled (`inputPassedOn`), by when Playwright's report of its typing is in: nothing guarantees that the report comes before the adapter tells that the key arrived. It needs no read of its own, and keeps no input behind it waiting (`underWay`). While no recording is under way the lifecycle keeps no input: a click a page still holds back then is passed on at once (`aside`).
- An end from outside always finishes, whatever the browser never answers: no state may wait for the browser without a time over the wait. A wrap-up has its time limit; stopping the trace, at a save and at a Clear, is asked with `within`, and the worker tells the lifecycle "requestFailed" for it when that time has passed and the lifecycle still waits for the answer (`awaitsAnswer`). A new wait on the browser that an end must pass through gets a time in the same way, and a state in `src/outsideEnd.test.ts`.
- A wrap-up's time limit is that wrap-up's: the worker ends it once the lifecycle has left the wrap-up, so it cannot pass for a later one.
- An input known from Playwright's report only, as typing, shows while it can still change. It is told to the timeline under its key (`fillKey`, its "before" and its id) once it has its start and every earlier input of its page shows, and again whenever its text or its latest read changes: its text follows every revision, and what it changed runs from Playwright's picture at its first report, which a revision keeps, to its latest read of its own page (when typing makes the page navigate, or the page closes, a fill's changes go up to the last read of its own page) (`showOrWrite`). It is final, and told once more, once something newer happened on its page, except that the focus a click's press moved can still go from its changes to that click's (`pressedAfter`); in a wrap-up, at the last: once Playwright's recorder is confirmed off, or, when the recorder ends, once the last snapshots are in (`writeDown`). A revision that comes after it is final sets only its text, while Playwright reported nothing newer on its page (`lastFill`). A revision on a page with no report since Record or Continue is of an Interaction from before, as typing more into a field typed in before a pause: it is a fill of its own. So is a revision once the page went to another document, by any navigation (`sameDocument`: a change of only the address's query or hash keeps the document, and the gate, the fill and its reads with it, so typing that writes itself into the address stays one fill): the page's gate forgets its last fill and its reports, and an input known from its report on that page takes no more revisions (`leftDocument`, `elsewhere`), so typing on the new page into a field with the same selector, which Playwright reports as an update of the fill before, is a fill of the new document's Visit, from a read of it. A wrap-up whose time limit passes writes what is complete all the same, and a fill that showed stays as it showed.
- Each "after" is no later than the next "before", for inputs the gate never holds too: one reported while an earlier one still waits for its "after" closes it with one shared snapshot (`carryOnReported`). The timeline does not rely on it: an Interaction that starts at a snapshot its entries have passed is written from its own start.
- What the page changed while paused is not the recording's. Continue has every page read once its inputs are held back, and the first snapshot of a page after a pause is added with `resumes`: the timeline compares it with nothing before it.
- Whether a recording is empty is the timeline's to say: `package` gives null until an Interaction is recorded, as the released recorder writes no package then.
- Discard and restore are commands like the others, applied only while paused. The lifecycle asks the timeline to keep the decision (`discard`, `restore` in `TimelineAddition`) and knows no entry: the timeline leaves an id it does not have alone. A discarded entry keeps its place and what it changed; the package writes it as the released recorder does, a stub, and a recording in which every entry was discarded still saves. Decisions go with the timeline: Continue keeps them, Clear drops them, Finish saves them.
- A new thing the timeline keeps is a member of `TimelineAddition`, which the lifecycle lists like any other thing to do. After each one the worker tells subscribers the Visits and entries if the timeline's list changed, an entry added or one replaced in place, under a new revision.
- Assert visibility is Playwright's own picking mode, which the lifecycle asks for with `pick` and hears of with "picking", whoever switched it. It takes effect only once no input is held back, and every wrap-up leaves it. An assertion Playwright reports takes one snapshot, which is its "before" and its "after", so it carries no Change Tree, and closes an Interaction that is still settling. When an input that is not held back, as typing on a page that lets inputs through, is reported while that snapshot is still being taken, the snapshot would come after the input: the assertion is then placed at its page's latest snapshot, and the input starts there too, so that a fill is measured from the page before its first key (`startReported`); the assertion still waits for its own snapshot, and finds the element it picked there (`targetRead`), as one a hover showed after the latest snapshot. The input's wait for a Settled Page starts once that snapshot is in. While picking, every page's gate leaves inputs alone: the picking click is Playwright's, and never reaches the page. Playwright's own picking box stays hidden with the rest of its overlay; every document draws the recorder's own outline, the highlight's look, over the element under the mouse, the deepest one as Playwright takes it (`followPicking` in `in-page/drawing.ts`), until an element is picked in any document or picking ends. It is hidden from the page's structure and from every input, so snapshots and their clickable marks stay as they are.
- The hover highlight is a command answered later, like Record, but by a key of its own (`keepReply`, `replyKept`), as one highlight follows another: the timeline says how the page as it is now is asked for the element (`locate`, "located"), then the browser draws it (`highlight`, "highlighted"). The element is an entry's target, or with `row` the element a row of its changes names; each is found by the ref the page's latest snapshot gives it while that snapshot lists it, so exactly that element lights up, and after that, a target by its recorded selector and a row's element by the selector of its label (`liveTarget`, `ElementLookup` in `recorded.ts`). A target the report's picture does not list is marked on its nearest listed ancestor (`byAncestor`): it is found by its selector first, since the ancestor's ref would light more than the element. A page has left its Visit once a new Visit starts, and, while paused, as soon as it goes to another address, unless only the query or the hash changed (core's `startsNewVisit`): the lifecycle tells the timeline of every address a page that had a Visit goes to while paused (`elsewhere`), the second as much as the first, and the timeline decides by the address. An entry of a Visit its page has left is looked for on the page as it is now: its target by its selector all the same, a row's element by the selector of its label, never by a ref of that Visit, which names nothing in the page's new document. A page that was closed highlights nothing. A label's selector enters the frame its element is in by the frame's own label. The browser draws on every element a selector finds, look-alikes included, and on the one element a ref names: a ref that names none or several is no element found. A selector's frames are entered one level at a time, every frame its part before each entry matches, and the boxes of all its matches in a frame are read in one call, moved by the frame's place in the page (`boxesOf`). The highlight's answer says whether it found any, and the window's chip shows by it whether hovering it finds something. Only the latest is drawn, and a highlight still drawn is cleared when the recorder leaves recording and pausing.

## Effect

The flows and adapters are written with Effect 4. The pure rules, the contract, the front door and anything injected into a page are not; lint enforces where `effect` may be imported.

- The documentation to use is the one shipped inside the installed package: `node_modules/effect/AGENTS.md` in this package's folder, which links to runnable examples in `node_modules/effect/ai-docs/` beside it.
- Most knowledge of Effect is from version 3, and many names changed in version 4. The rename guide: <https://github.com/Effect-TS/effect/blob/effect@4.1.4/MIGRATION.md>.
- Production code uses only the stable `effect` package: no `@effect/*` package and no `effect/unstable/*` module, so none of Effect's own HTTP, socket or process modules. Tests may use the Vitest helper for Effect, `@effect/vitest`. The test clock is in the stable package, at `effect/testing`.
- Check every name in the installed type definitions, `node_modules/effect/dist/*.d.ts`, never from memory.

## The supported Playwright range

[`playwright-range.json`](playwright-range.json) beside this file states the range: the oldest Playwright the recorder starts on and the newest it is verified on. The adapter, CI's per-version job and the weekly canary read it. It is not the root `playwright-range.json`, which is the published packages' `@playwright/test` range. Below the range, or with no Playwright recorder found, starting fails with an error that names the range; above it, the recorder still records.

A private part of Playwright that the adapter uses gets a test in the compatibility suite (ADR-0052), which proves the adapter works on each supported Playwright version. To verify a new Playwright minor, run the suite and the main end-to-end test on it, then move `lastVerified`.

## Testing

Run from this directory inside the repository's Devbox shell. `pnpm test` needs the build, since `src/publicTypes.test.ts` reads it; Turbo's `test` task builds first.

- `session/domain/lifecycle.test.ts`: the lifecycle as a table: things that happened, in order, and the lists it must ask for. No browser, no clock. Each bug path of the lifecycle model is a row, and a row that keeps one of the spec's rules says which. The rows written before typing showed while it was typed read the lists through `writes`, which keeps a fill's final write only, under no key, telling it by the fill having left the lifecycle's inputs (`showingIn`); what shows of a fill before then has its rows in "the lifecycle, for a fill while it is typed", one or more per rule.
- `timeline/domain/timeline.test.ts`: snapshots and reports in, package text out, including an input's "before" read from Playwright's picture (`reportPicture.ts`). Expected text comes from `timeline/domain/fixtures`, whose README says where each file is from, or is written out in the test; it is never produced by the code under test.
- `timeline/domain/elementNames.timing.test.ts`: how long labelling every element of a large list takes, by the shape of its items. `pnpm test` leaves it out; `pnpm test:timing` runs it, with `AYME_LABEL_TIMING` set to the file it writes the times to.
- `src/recorder.test.ts`: the handle, on the scripted browser.
- `src/toolbar.test.ts`: the toolbar's page function, on the scripted browser: its commands, its updates and how it is told the end.
- `src/window.test.ts`: the window's server, on the scripted browser, through a tRPC client of the test's own: its files, its loopback check and its channel.
- `src/recording.test.ts`: a recording on the scripted browser, where the test plays a click, a Settled Page and a report by hand and moves the clock, down to the package on disk.

## The lifecycle model

[`lifecycle-model/`](lifecycle-model/README.md) is a TLA+ model of the lifecycle, checked with TLC against the rules the recorder must keep. When a change alters the order of events, what the recorder waits for, or a promise it makes, run the model and update it, with the `verify-recorder-lifecycle` skill.

## Known limits

Users read the recorder's known limits in [the CLI's README](../cli/README.md#known-limits), and a coding agent reads what a package holds in [the `ayme-recorder` skill](../../skills/ayme-recorder/SKILL.md). Why some of them are so, for whoever changes the engine:

- A fill is measured from the page before its first key, except when it follows an input known from its report only before the page went quiet, with no held input between: typing into another field the page moved the focus to by itself, or typing right after a choice in a dropdown or an upload. Its first key is not held, as the page lets inputs through, and the earlier input is still open: the fill starts where that one ends, at a read taken after its first key, so that key's change is listed under the earlier input.
- A page's first click can leave out the focus its press moved: the page is first read for that click, after its press moved the focus, and no read shows where the focus was before. Telling it would take the gate noting the focused element at the press, a datum the adapter and the lifecycle would carry.

- The toolbar's host element stays in the trace's page snapshots as an empty element: Playwright's snapshotter leaves out only a few kinds of element, none of which can hold the toolbar. The trace holds no screenshots, so the toolbar is in no picture. Like the toolbar, the highlight's host element is in the trace's page snapshots while it is drawn.
- Finding the element of a hover highlight adds actions to the trace: Playwright's public locator counts the element a ref names and reads its box, or reads the boxes of every element a selector names in one call per frame, and the first highlight on a page opens a DevTools session there. The package's position numbers stay right, as they are the stock trace tool's own numbers for the snapshot marks (the compatibility suite checks a highlight between two snapshots). Drawing it adds nothing.
- Playwright reports an assertion's target by a selector only, which it built when the element was hovered: by the time of the report it can match more, as a card the hover opened. So the picking outline keeps the element under the mouse at the picking click, on the window before Playwright's recorder takes the click (`followPicking`), and the adapter takes, of the elements the selector matches, the nearest around it (`pickedAmong` in `in-page/calls.ts`); with none kept or none around it, the selector names an element only when it matches one alone, never the first of several. The adapter reads the ref its own snapshots give that element, or its nearest ancestor they list, from a public snapshot of the element and of each ancestor in turn (`withPickedRef` in `stockBrowser.ts`), and the report carries it (`snapshotTarget`): the timeline then names it as it names a click's target. A step the snapshots name no element for is named by its selector's words (`selectorWords` in `timeline/domain/elementNames.ts`): a role and name as a label reads them, or else Playwright's own locator for the selector, which the adapter puts on every report (`locator`, from Playwright's `Locator.toString()`), so the window never shows an `internal:` selector as a step's element. Every entry also carries those words for whoever shows its selector (`targetLocator`); the package keeps the selector only. Reading it adds actions to the trace, as a highlight's lookup does. Its highlight finds it by its selector, as it finds every target.
- A document that starts while Playwright picks, as one a page goes on to by itself, starts as the documents open then do: its gate leaves the picking click to Playwright, and it draws the outline. Every change of Playwright's mode adds a start for documents that load from then on (`startPicking`, the latest wins), and the adapter tells of the change once that start is added. The start is kept in the document, as the gate's own is (`startGate`), and the gate reads it when its script runs: it holds whichever script runs first, in a page and in a frame.
- The outline while picking is in the trace's page snapshots while it is drawn, as the highlight is.
- A double click can reach the page as a single click: the gate checks once that the person's button is up before a held click is sent on, and a press that comes after that check but before the click's own press and release is ended by the re-sent release, so the second click and the `dblclick` never happen. Closing the gap means either holding a single click for the person's double-click interval or holding the person's press while a click waits, and both change something chosen deliberately (clicks reach the page in about 15 ms; presses and drags are never held), so the choice is the owner's.
